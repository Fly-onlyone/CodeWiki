# CodeWiki — agent instructions

CodeWiki is a Windows-only native desktop app plus a Rust backend that generates and maintains a codebase wiki (an Obsidian vault at `<repo>/obsidian/`) for humans and coding agents. `ROADMAP.md` records what is built and what is verified.

## Hard rules

- **No WebView.** The UI is native Rust on GPUI (`gpui-kit`). Do not add a browser, WebView2 or Electron dependency.
- **The app talks HTTP only.** `codewiki-app` gets all data from the backend through `cw-client`. It may link `cw-illustrate`, `cw-mermaid` and `openui-lang` to draw, never the index, parser or wiki crates. Three exceptions concern the app itself: it links `cw-update` to ask GitHub for a newer release and to replace its programs, `cw-telemetry` to send its own error reports, and `cw-core` to read and write `agents-off.json` (`cw_core::agents_off`), the list of folders kept from coding agents, and `auto-explain.txt` (`cw_core::auto_explain`), the switch for auto explaining. Both are settings of the agents on this machine and not of a backend.
- **Error reports are opt-in and scrubbed.** Nothing goes to Sentry unless `SENTRY_DSN` is set or the user turned on "Send error reports" in a build that carries a DSN. Never add a field to a report that the logs may not hold, and never weaken `cw_telemetry::scrub`.
- **Never overwrite a human-edited note.** Changes to such notes go through the proposal queue.
- **The index is a cache.** Everything in it must be rebuildable from the repository and the vault. Bump `SCHEMA_VERSION` in `crates/cw-index/src/schema.rs` on any schema change; old indexes are dropped and rebuilt.
- **Keep builds small.** Do not loosen the `[profile.dev]` settings in the root `Cargo.toml`; debug builds once reached 44 GB. Run `pwsh scripts\clean.ps1` after long sessions; it keeps what the `codewiki-app` run configuration builds, so starting the app afterwards compiles nothing, and `-All` removes everything.
- **The programs must run on a clean Windows.** `.cargo/config.toml` links the C runtime statically; without it they need `vcruntime140.dll`, which a clean machine may not have. A program the app starts in the background is started with `CREATE_NO_WINDOW` (`crates/cw-client/src/lib.rs`), or Windows opens a terminal window for it. This machine has the runtime and a graphics card, so neither failure shows here; `scripts/vm` is where they show.

## How the parts connect

- **Who opens the index.** The CLI and `codewiki serve` (`cw-server`) open the index directly. The app and the MCP bridge never do: they call `cw_client::Backend::connect` in `crates/cw-client/src/lib.rs`, which uses the first of these that works:
  1. `CODEWIKI_URL` with `CODEWIKI_TOKEN`.
  2. The backend saved in `remote.json` in the data directory, while it is in use (`crates/cw-client/src/remote.rs`). One that does not answer is an error: `connect` never falls back to a local backend by itself, because one started in its place would show other wikis, or none. Only `cw_client::use_local` goes back, and it keeps the address and token.
  3. The URL and token in `backend.json` in the data directory, when `/v1/health` answers.
  4. A new `codewiki serve`, started from the binary beside the caller or from `PATH`.

  `Backend::origin` says which of these it was. The app and the MCP bridge both follow `remote.json`, so an agent and the app read the same wikis.

  The backend ends with the app, and the app ends on Quit, not when its window closes (see "The tray" below). On Quit the app asks the local backend it uses to stop (`POST /v1/shutdown`), whoever started it, and does not wait. A backend named by `CODEWIKI_URL` or saved in `remote.json` is left alone (`cw_client::uses_remote`). The backend finishes the requests it is running, an update of a wiki included, then exits; an agent's MCP bridge that shared it starts a new one on its next call. Quit is refused while a note has unsaved edits (`AppView::quit` in `main.rs`).

  A backend started before a rebuild keeps serving the old code, for as long as something keeps it running (the CLI's `serve`, an MCP bridge, an app hidden in the tray, an app ended by force). Stop it after changing a backend crate (`POST /v1/shutdown` with the token, or end the process). A rebuild keeps the version, so `connect` cannot tell; it does replace a local backend whose version is older than the client's, which is what an update leaves behind, and never a newer one. A backend that ends before it answers is reported at once; the app then offers "Try again", and the MCP bridge tries again on its next call. The bridge also drops a backend it was using once that one stops answering, and connects anew.
- **Updates.** `cw-update` checks GitHub's latest release (`CODEWIKI_UPDATE_URL` replaces the API address in tests), downloads the zip into `<install>\.update`, verifies its `.sha256`, runs the new `codewiki.exe --version`, has the app stop the backend, then renames each installed entry to `<name>.old` and moves the new one in. Windows lets a running program be renamed but not replaced, so the app and an agent's bridge keep running from the `.old` file. Every move is written to `.update\swap.json` before it is made and undone on the first failure; `recover_and_clean`, at the app's start, undoes a swap cut short and deletes the `.old` files no longer in use. After a swap the app writes the new version into `DisplayVersion` of the Settings → Apps entry, when that entry exists (the setup program makes it; `install.cmd` does not). Only an installation made by `install.ps1` updates itself (`uninstall.ps1` beside the programs, `install.ps1` not). The app's part is `crates/codewiki-app/src/update.rs`; the check runs once a day (`update_checked.txt` in the settings folder) unless `update_check.txt` says `off`: at the start, and every hour a running app looks whether the day is over, since an app in the tray runs for weeks. It only ever offers. Before it starts the new version, the app gives up its place as the running instance (`instance::release`), or the new app would hand over to the one that is ending.
- **Where state lives.** The index and the backend's state are in `cw_core::paths::data_dir()`: `CODEWIKI_DATA_DIR` when set, otherwise `%LOCALAPPDATA%\CodeWiki`. `auto-explain.txt` is there too (`on` or `off`; a missing file means on, anything else or an unreadable file means off; the app writes it, and `codewiki hook session-start` and the app read it). Two settings files are there too: `settings.json`, which only the backend writes, and `remote.json`, which only `cw-client` writes, so neither program can overwrite the other's change. The vault is `<repo>/obsidian/`. The app's settings (`theme.txt`, `motion.txt`, `zoom.txt`, `log_level.txt`, `last_repo.txt`, `update_check.txt`, `update_checked.txt`, `tray_hint.txt`, `open_last.txt`, `backdrop.txt`, and `recent_repos.txt`, which holds one folder per line, newest first) are in `%APPDATA%\CodeWiki` (`prefs.rs`; the app deletes the old `model_hint.txt` at its start), and so are the two files of the running instance (`instance-<key>.lock` and `.txt`). `error_reports.txt` is there too: the app writes it, and every program that reports reads it itself (`cw_telemetry::consent`). Two things are outside it, in the user's registry, and `uninstall.ps1` removes both: "Start with Windows" is the value `CodeWiki` under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` (`autostart.rs`; the value is the whole setting), and the name Windows shows the app's one notification under is `HKCU\Software\Classes\AppUserModelId\CodeWiki.App`. A debug build (`cw_core::DEV_BUILD`, `cfg!(debug_assertions)`) uses `CodeWiki-Dev` in place of `CodeWiki` under both folders (`cw_core::paths::APP_FOLDER`), calls itself "CodeWiki Dev" in its title bar, sidebar and tray (`cw_core::APP_NAME`), and shows its notifications as `CodeWiki.App.Dev`. A run from the sources therefore never finds, uses or stops the backend of an installed CodeWiki, and never reads its index or settings; it starts with no repositories and the default embedder. The variables still win over both folders. `cw-client` passes its data folder (`CODEWIKI_DATA_DIR`) to a backend it starts, so a release `codewiki` found on `PATH` writes `backend.json` where the caller waits for it.
- **Logs.** Every program logs through the `log` crate and the one logger `cw_core::logs::init` installs: each record goes to `<name>.log` and to standard error, and a file over 1 MB is moved aside to `<name>.old.log`. The folder is `logs\` under the data directory (`CodeWiki-Dev\logs\` for a debug build), or `CODEWIKI_LOG_DIR` (a relative path is taken from the working folder). The RustRover `codewiki-app` configurations set it to `logs`, so a run from them writes to `<repo>\logs\`, which git ignores. The app writes `app.log`, GPUI's records and every panic included. `codewiki serve` writes `backend.log`: its start, with the writer and embedder in use; failed, refused and slow requests; each step of a sync with its time, and a summary; failed LLM calls; its stop. The MCP bridge writes `mcp.log`. Other CLI commands print warnings only, and the session-start hook prints nothing. `CODEWIKI_LOG=debug` keeps more, such as every request and each LLM call. The app's level can also be chosen in Settings → Diagnostics: it is kept in `log_level.txt`, applied at once with `logs::set_level`, and the variable wins over it. `cw-client` passes its log folder to a backend it starts and leaves the backend's standard error unconnected, because a pipe nobody reads any more would stall it. A backend that was already running keeps logging where it was started. Never log a token, a key, a query string, a prompt, an LLM answer or note text. "Open logs folder" (palette, Settings, the page shown when the backend is not reachable) shows the folder in Explorer. Read the logs before guessing why something did not start.
- **Error reports.** The app, `codewiki serve` and the MCP bridge start their log with `cw_telemetry::init` instead of `cw_core::logs::init`. It installs the same file logger, wrapped in Sentry's when reports are on: an Error record becomes a report, Info and Warn records become its breadcrumbs, and a panic is reported by Sentry's own hook with its backtrace (the `panic` record is left out, so it is not reported twice). Other CLI commands and the session-start hook never report.
  - **When.** `SENTRY_DSN` in the environment turns reports on for that process and the ones it starts. Otherwise a build made with `CODEWIKI_SENTRY_DSN` set carries that DSN (the release workflow sets it from the repository variable `SENTRY_DSN`), and reports only while `error_reports.txt` says `on`: Settings → Diagnostics → "Send error reports", off by default. Turning it on applies from each program's next start; turning it off applies at once, because every report reads the file again (at most every five seconds). A dev build without either never starts the SDK.
  - **What.** `cw_telemetry::scrub` runs on every event and breadcrumb: no host name, no user, no query string, headers, cookies or body of a request, every absolute Windows path replaced by `<path>`, a loaded program named by its file name alone. Names are not scrubbed: a log line that names a repository, a note or a remote backend's address reaches Sentry as it is, and README and the Settings page say so. The project has "Prevent Storing of IP Addresses" on and the Advanced Data Scrubbing rule `[Remove] [Anything] from [$user.geo.**]`. Sentry's Relay looks up a city and country from the address a report arrives from before it drops that address, and the Rust SDK (0.49) cannot ask it not to (`sdk.settings.infer_ip` is not in it, and Relay's lookup ignores that setting anyway), so the rule removes them. README and the Settings page promise that Sentry keeps neither the address nor its city and country: both are project settings in Sentry, not code, and must stay on. Each report is tagged `program` (`app`, `backend`, `mcp`), its release is `codewiki@<version>`, its environment `SENTRY_ENVIRONMENT` or `development`/`production` by build.
  - **Traces.** The backend traces a request (`trace_request` in `crates/cw-server/src/api.rs`) as a transaction named by method and route (`GET /v1/repos/{id}/search`), with no request data: Sentry's own tower layer would send the query string, and the SDK has no hook that scrubs transactions. `/v1/health` and `/v1/status`, which clients poll, are not traced. `SENTRY_TRACES_SAMPLE_RATE` sets the share (0.1 by default). There is no profiling: the Rust SDK has none.
  - **Check.** `codewiki sentry-test` (hidden) sends one test report, `--panic` a panic; both refuse when reports are off.
- **The tray.** Closing the window (the X, Alt+F4) hides it; the app stays, with an icon in the notification area (`tray.rs`, drawn by the `tray-icon` crate). A click on the icon shows the window, a right click opens a menu, and Quit, there and in the palette, ends the app. The tooltip and the menu's first rows say what the app is doing: the open repository, whether a wiki is being updated, and when an agent's MCP bridge last called. The app does not know the last two by itself. It asks the backend every 5 seconds (`GET /v1/status`, `cw-server/src/activity.rs`): the route lists the updates that are running, whoever started them, and the time of the last request that carried `x-codewiki-client: mcp`, which only the bridge sends (`Backend::with_client`). The route also reports `notes_rev`, a counter the backend raises whenever a vault or a claim changes (a claim that runs out counts); the app refetches the waiting list when it moves (`take_status` and `load_waiting` in `crates/codewiki-app/src/main.rs`), which keeps the toolbar's "To explain (N)" and the Waiting notes page current. `status.rs` puts that into words; `tray::rows` is the menu as plain data, and both are tested without a tray. The menu keeps its shape and changes its rows in place, because a menu rebuilt while open closes under the pointer. Without a tray icon (Windows refused one) closing the window ends the app, as it did before.

  Three rules keep this from breaking GPUI:
  1. A click on the icon or a menu row arrives in a window procedure, and a second launch on another thread. Neither may touch the app. They send an `Event` through a channel, and one task of the app's view carries each out (`AppView::listen`).
  2. Hiding and showing the window (`win32::hide`, `win32::show`) make Windows call back into GPUI before they return. They are called only in that task, between two updates, never inside one.
  3. A window that was never shown (`--tray`) is first shown by `activate_window`, which also puts it in its place; `ShowWindow` before that would show it where Windows puts a new window.

  `win32.rs` is the only module of the app with `unsafe` code. Keep every Win32 call of the app there. The workspace has one more such module, `cw_core::secret`, for the Data Protection API. Every `unsafe` block says why it is sound in a `// SAFETY:` comment above it; clippy (`undocumented_unsafe_blocks`) and `codewiki check` both report one without.
- **One app per program.** Starting the app while it runs hands what the launch was asked to open to the running app, which shows its window, and the launch ends (`instance.rs`: a lock file the running app holds, and a line of JSON to a local port). "The same app" is the same program file, so an installed copy and a development build stay apart. `CODEWIKI_INSTANCE=new` starts a separate app whatever is running; a check or a test that must not bring another window to the front sets it. A launch that can neither take the lock nor reach the running app runs by itself after ten seconds: the app never refuses to start.
- **Which repository the app opens.** The command line is `codewiki-app [--tray] [<folder> [<view>]]` (`startup.rs`); a flag may stand anywhere and is never taken for a folder. `--tray` starts with no window on screen, as Windows starts the app at sign-in. The first of these that applies:
  1. The first argument that is not a flag.
  2. The working folder, only when it holds `.git` or a CodeWiki vault.
  3. The repository opened last.
  4. The newest repository in the recent list that is still registered.

  `startup.rs` checks the first three; `connect` in `main.rs` falls back to the fourth.

  Whatever opens, the app starts on Home (`live::home_page`, `Page::Home`), unless "Open the last repository" is on (Settings → Appearance → Startup, `open_last.txt`, off by default): it then starts on the wiki map of the repository it opened, and on Home still when that one has no wiki. The view `home:` is always Home. Home has "Open folder…" and lists every registered repository, the most recently opened first. Home fills the window: no sidebar, toolbar, tabs or details pane (`fills_window` in `main.rs`). The same goes for the pages shown before a repository has loaded. A second argument naming a view or note starts the app there instead, in a repository that has a wiki; one without lands on Home, which offers to sync it. A second launch that names a folder or a view opens it in the running app.

  Never let a folder the user did not choose be registered: the backend would index all of it.
- **Repositories whose folders are gone.** `GET /v1/repos` reports for each repository whether its folder still exists (`present`). The backend checks this, because the paths are on its machine. The app never forgets one by itself: a folder can be away for a while (a drive that is not plugged in, a share that is offline). Home lists such a repository under "Folder not found" with a Remove button, and only that button deletes it (`Action::ForgetRepo`, `DELETE /v1/repos/{id}`). The deletion forgets the repository only. The index files stay, and opening the folder again restores it under the same id.
- **Generation.** `cw_wiki::service` holds the operations that the CLI, the server and the MCP tools share. `service::update` rescans the repository into the index, then `generate::generate` scans, plans, freezes names, renders, lints and writes. `cw_vault::lifecycle` decides for each note whether it is written, proposed or left alone. Bump `TEMPLATE_VERSION` in `crates/cw-wiki/src/generate.rs` when a rendering change should refresh every note.
- **CodeWiki calls no language model.** There is no provider, no prompt and no key for writing notes. Do not add one: a coding agent with the plugin writes what rules cannot, it reads any file it needs, and it is already signed in.
- **Who writes a note.** Each `## ` section of a note belongs to rules or to a coding agent, by the note's kind: `NoteKind::agent_sections` in `crates/cw-vault/src/note.rs`. Rules own every fact (summary, Source, Items, Depends on, Used by, See also, an integration's Used for and Configuration, a pattern's When to apply and The pattern). The agent owns the rest (What it does, How it works, Gotchas, Wire-up, Auth mode, Why, Don't). A flow's diagram and an operations note's commands are facts inside a section whose prose is the agent's (`NoteKind::fact_fences`): the rule's blocks first, the agent's prose after.
  - **One weave, two directions.** `cw_vault::explanation::weave(base, agent_sections, kind)` puts an agent's sections into a note and leaves the rest of `base` as it is. When an agent submits, `base` is the note on disk. When the code changes, `base` is the fresh draft and the agent's sections come from the old note (`extract`). `note::split` and `note::join` are the one definition of a note's layout; `render.rs` builds its notes with `join`.
  - **The record.** `NoteEntry::explained` holds the headings the agent wrote, the files it wrote them from with their hashes, and the commit; `model` names the agent; `behind` holds why the explanation may be out of date. A submission does not make a note "edited by a person": it updates `body_hash`.
  - **At a sync** (`generate.rs`): the draft changed and nobody edited the note, so `Action::Merge` writes the weave. Only a file of `explained.sources` changed: the note stays and is marked `behind`. A person edited it: a proposal, whose text keeps the agent's sections. The file is gone: rules write the note again and `explained` is cleared. A link of the agent's to a note that the run removes becomes plain words.
  - **The way in** is `crates/cw-wiki/src/explanations.rs`: `queue` (notes behind first, then never explained), `brief` (one note, the agent's sections, the files to read, the limits) and `submit`. A submission holds sections and pictures, never a whole note, so an agent cannot change a fact. `submit` checks everything, then answers `Saved`, `Issues` (every fault at once, nothing written), `Changed`, `SyncFirst` or `Proposed`. The routes are `GET /v1/repos/{id}/explanations` and `GET`/`PUT /v1/repos/{id}/explanation`; the `PUT` answers 200 for every outcome, because a client keeps only one line of an error. The MCP tools are `list_waiting_notes`, `get_note_brief` and `submit_note`. **Claims** (`crates/cw-server/src/claims.rs`, in memory only): `GET /v1/repos/{id}/explanations?agent=<id>` (1 to 64 characters) leaves out the notes other agents hold and lends the notes it lists to that agent for 30 minutes (`cw_core::CLAIM_MINUTES`); `all=true` lists every waiting note, with the claimed rows marked, and cannot go with `agent`. The `PUT` takes the same `agent`: a note it saves or proposes is freed, and the agent's other claims are renewed. `list_waiting_notes` has `claim`. The bridge gives every listing with `claim: true` an agent id of its own (`<pid>-<start nanos>-<count>`, `ClaimIds` in `crates/codewiki-mcp/src/main.rs`), because the main agent, its note-writer and one launched after `/clear` share one bridge; it remembers which id each listed note went to and `submit_note` sends that id, or the bridge's own `agent_id` for a note not claimed through it. A listing with `claim: true` therefore does not hand back the notes an earlier listing of the same session holds.
  - **A note a person edited is never written**, by a sync or by an agent. An agent's text for it is a proposal of kind `agent`, with its pictures; a sync's is of kind `sync`, and neither replaces a pending one of the other. `explanations::approve` and `reject` treat each by its rules. After an agent's proposal is approved the note stays its owner's: `body_hash` keeps the old value.
  - **Pictures** are a coding agent's, never the rules': a picture explains what a thing is for, which rules cannot know. The library (`cw_illustrate::library`) has four components, `Picture`, `Flow`, `Step` and `Callout`, and `review` holds a picture to its limits. A note's pictures are in `<Note>.openui` beside it, each under a `# section: <heading>` line (`parse_pictures`, `serialize_pictures`); the Markdown stays clean. A sync deletes the picture file of a note no agent explained. The app draws each picture under the heading of its section (`markdown::prepare_note_with`, `illustration.rs`). When you add a component: the library, `review`, the renderer's `match`, `plugins/claude-code/skills/write-notes/pictures.md`; tests pin the last three to the first.
  - **The agent view.** `query::agent_view` is what `read_note` gives an agent and what "Agent view" shows in the app: no pictures, and no `How it works` while rules wrote it. A section the agent wrote stays in.
  - **The skill** is `plugins/claude-code/skills/write-notes/SKILL.md`, which Claude Code also offers as `/codewiki:write-notes`. `crates/codewiki/tests/plugins.rs` pins every tool, argument, answer, section and number it names to the code. Codex has its own copy, `plugins/codex/skills/write-notes/SKILL.md`. The session-start line about waiting notes (`briefing.rs`) states a count and is an order only when auto explaining is on (`explain_for`): the switch is on, `source` is `startup`, `resume` or `clear`, and neither the session's folder nor the vault root found above it is a linked git worktree (`cw_wiki::git::is_linked_worktree`). The hook leaves the order out when the host reports plan mode (`permission_mode`, which Claude Code's SessionStart input may not carry); the order itself tells the agent to skip it in plan mode. With the switch off the hook does not read stdin. Then, for Claude Code, the first message launches the agent `plugins/claude-code/agents/note-writer.md` (`codewiki:note-writer`: Sonnet, background, up to 20 notes, `list_waiting_notes` with `claim: true`); for Codex, the `write-notes` skill runs after the first request (`codewiki hook session-start --agent codex`, which the Codex `hooks.json` and `config.toml` sample pass). In every other case the line is a fact and says to write notes when asked or for files changed. A folder kept from coding agents gets no briefing at all, as before. `plugins.rs` pins the skills, the agent and the order's wording. Limit: a `codewiki update` run outside the backend (on the command line) or an edit in Obsidian does not move N until the next `notes_rev` bump or until the repository is opened again.
- **Folders kept from coding agents.** `cw_core::agents_off` reads `agents-off.json` in the data directory (`{"version": 1, "folders": [...]}`): an entry covers its folder and everything below it, and a folder that holds an entry is blocked too, because indexing it would index the entry's code (`agents_off::blocking`: `Block::Covered` first, then `Block::Contains`; folders are compared by whole names, so `D:\work\client` neither holds nor lies in `D:\work\clients\x`). A list that cannot be read, or that has an empty or relative entry, fails closed. The texts people and agents read are functions of the module (`refusal`, `repo_refusal`, `unreadable`); the bridge, the command line and the app call them, and the exact-text tests pin them there. Three things obey the list. `codewiki hook session-start` prints nothing when the project folder or its vault root is covered or holds an entry. The MCP bridge (`screen` in `crates/codewiki-mcp/src/main.rs`, `guard.rs`) refuses every tool when a session folder (the current folder or `CLAUDE_PROJECT_DIR`) is covered or holds an entry, with `refusal`, which names the entry. A `repo` argument (path, id or name) that is or reaches such a folder gets `repo_refusal`, which names no path and stops that repository alone. `screen` costs at most one `GET /v1/repos`; `Bridge::call` then checks the repository the call reaches by the id it resolved, through one listing, so a lookup that failed in `screen` or `repo_id`'s fallback to a name cannot reach a kept repository. A refusal found there travels as an error marked `REFUSED`, and `answered` in `call_tool` turns it into a normal text result. `list_repos`, `get_workspace` and `get_contracts {workspace: true}` leave out covered and holding repositories, and refuse when the list cannot be read. The bridge's tests serve canned JSON from a stand-in backend named by `CODEWIKI_URL`. The plugin skills tell the agent to stop at either refusal; `plugins.rs` pins their lines to the two texts. `codewiki agents off|on|list|status` and the app (Settings → Repositories, Home rows, palette) write the list; the app does so through `cw-core`, not the backend. Home shows four states of a project (`live::Kept`: open, its own entry, under a parent entry, holding an entry), worked out in `refresh_agents_off`. With a remote backend the bridge reads the backend's repository paths as local paths: one that names a kept folder here, or holds one, is refused and hidden (on Windows a Linux path reads as a path on the current drive), and the others are not hidden. A `repo` given as a path is always read as a local path, so an agent cannot register a remote backend's new repository by its path there. Limit: a visible route called only by a hidden repository leaves the matched list in `get_contracts` and does not show as unconsumed (`guard::hide_in_contracts`).
- **Settings.** The embedder, its model and the keys and addresses each have an environment variable and a place in `settings.json`: `CODEWIKI_EMBED`, `CODEWIKI_EMBED_MODEL`, `CODEWIKI_LMSTUDIO_URL`, `CODEWIKI_LMSTUDIO_KEY`, `CODEWIKI_LLAMACPP_URL`, `CODEWIKI_LLAMACPP_KEY`, `CODEWIKI_LEMONADE_URL`, `CODEWIKI_LEMONADE_KEY`, `CODEWIKI_MISTRALRS_URL`, `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `OLLAMA_HOST`. `cw_core::settings::Resolved` gives the value in effect and where it comes from: the variable when it is set, then the file, then the default. A setting is named by its variable, and the table of them is `settings::ALL`.
  - **Who reads them.** `cw_wiki::semantic::configure` puts the embedder in a slot that can change while the program runs; the server calls it at its start and after a change, the CLI at its start, so a change needs no restart. `from_env` in `cw-embed` reads the environment alone.
  - **Retired settings.** The sections `llm`, `anthropic` and `cliproxy` held the settings of the writer CodeWiki once called itself, two of them an encrypted key. `settings.json` keeps sections it does not know, so these are removed by name: `settings::RETIRED_SECTIONS`, at the start of `serve` (`drop_retired`) and on every `update`. A retired variable that is still set gets a line in the log; `CODEWIKI_EMBED_DEVICE` is one of them.
  - **Routes.** `GET /v1/settings` describes every setting; `PUT /v1/settings` changes the fields it names (`null` clears one); `POST /v1/settings/test/embed` sends the chosen embedder one small request (`probe`) and answers 200 with `ok` true or false. The work is in `crates/cw-server/src/settings.rs`. A field whose variable is set is refused. A server that listens beyond this machine refuses every change (`ServerConfig::settings_writable`): someone holding its token could point a provider's address at their own host and be sent the API key.
  - **Secrets.** An API key, and the token in `remote.json`, are encrypted for the current Windows user by `cw_core::secret` (the Data Protection API), one of the two modules of the workspace with `unsafe` code (see "The tray"). No route returns one: a key is reported as unset, saved, given by the environment or unreadable, with the last four characters of a saved one. Another system cannot save a secret and takes it from the environment.
  - **Stale vectors.** A changed embedder leaves the old vectors in the index until the next update. The index records which embedder made the vectors of each kind of document (meta key `vectors_embedder:<kind>`), and a search compares only those the current embedder made; until the update it is full-text alone. While a run replaces another embedder's vectors the key holds a marker that is no embedder's name, so a run cut short never counts as current; `vectors_waiting:<kind>` says whether documents still wait, and `semantic::behind` reads both.
  - **The model field.** `embed.model` is a model name of the chosen server. Model names do not carry across servers, so `settings::change` clears it on any change of provider that names no model, unless the environment sets it. A server provider with no model cannot be built: `embed.problem` says to choose a model, and search is full-text alone until one is named.
  - **Tests never read the machine's settings.** The server reads its environment through `ServerConfig::env`, which the route tests replace, and the embedder slot holds what the environment alone names until `configure` is called. Keep both, or a test calls the provider configured on the machine that runs it.
- **Embedding servers.** CodeWiki runs no embedding model itself and never downloads one: the user runs a server, and CodeWiki asks it for vectors. Do not bring a model engine back, under any name.
  - **Providers.** `local` (word forms, in process), `lmstudio`, `ollama`, `llamacpp` (Llama for Windows and `llama-server`), `lemonade`, `mistralrs`, `openai` and `none`, in that order on the page (`cw_embed::PROVIDERS`). Defaults: LM Studio `http://127.0.0.1:1234`, Llama `http://127.0.0.1:9931`, Lemonade `http://127.0.0.1:13305`, mistral.rs `http://127.0.0.1:1234`, Ollama `OLLAMA_HOST`. LM Studio, Llama and Lemonade have an optional key (`CODEWIKI_LMSTUDIO_KEY`, `CODEWIKI_LLAMACPP_KEY`, `CODEWIKI_LEMONADE_KEY`); mistral.rs has none; `openai` needs `OPENAI_API_KEY`. A server provider needs a model. Spike S5 in `spikes/VERDICTS.md` records what the built-in engine measured, before it was removed.
  - **One client.** `OpenAiEmbedder` in `crates/cw-embed/src/lib.rs` serves every OpenAI-style provider, given a `Server`: its address, key, extra body fields and the name used in errors and in the vector name (`<provider>:<model>`). Texts go in batches of 64, each cut at 8,000 characters. Its quirks sit in one place:
    - an address pasted with `/v1` works like the bare one;
    - a 401 or 403 names the key setting to fill in;
    - a batch refused as too long (HTTP 400, 413, 422 or 500 with a message about length) is sent once more with each text cut to 2,000 characters; refused again, its texts go one at a time (`one_by_one`), and a text refused alone once more cut to 400 characters (`TINY_CHARS`), its prefix kept; a text still refused is an error;
    - mistral.rs is sent `truncate_sequence: true`, or a long text is an error;
    - llama.cpp and mistral.rs embed with the model they hold, whatever `model` names: until an embedder instance's first call succeeds, it reads the server's `/v1/models` (`check_listed`) and fails with "<server> does not list <model>; choose a model it serves" when the model is not there. The Settings page warns the same way for any server whose list lacks the chosen model;
    - a request waits 120 s (`REQUEST_TIMEOUT`); the first call of an embedder instance waits 300 s, so that a server can load a model.

    An embedder error never quotes a text it was given.
  - **Model lists.** `GET /v1/settings/embed/models` lists what the provider in effect offers at its address in effect: `{ provider, reachable, models: [{ id, embedding, loaded }], problem }`, embedding models first, 10 s at most. The parsing for each server is beside its provider in `cw-embed`. Settings → Semantic search fills its Model select from it, and falls back to a text field when the server does not answer.
  - **Prompt prefixes.** `crates/cw-embed/src/prefix.rs` holds the text some models expect before a query and before a document: `gemma`, `qwen3`, `nomic`, `mxbai`, `bge` and `e5`, matched by the model's name, the first rule winning. A rule adds `+<id>` to the vector name, so vectors made with and without a prefix are never compared. It applies to every HTTP embedder. Each prefix is the one on the model's card; a test pins a model name for each rule.
  - **The job.** `crates/cw-server/src/embed_job.rs` finishes embedding after a Sync, for every embedder on every platform. It embeds with no lock held and takes `write_lock` for each batch's write alone; one job runs at a time, in the background, nothing of it on disk; a run that an update overtakes starts over (`Inner::updates`). The routes are `GET /v1/embed/job`, `POST /v1/embed/reembed` and `POST /v1/embed/cancel`; a backend that listens beyond its machine refuses all three. `/v1/status` reports the job as `model_job`, a name kept from before. A failed batch ends the job with its error (shown on the Settings page, kept in the log); the repository stays behind, nothing retries, and the next Sync, Test or reembed tries again. A backend that starts with a repository behind tries once.
  - **Updates stay quick.** An update of a wiki embeds for a second in each of its steps and leaves the rest to the job (`semantic::set_inline_budget`).
  - **From the built-in model.** `cw_core::settings::retire_builtin` runs at the start of `serve`, beside `drop_retired`: a saved `embed.provider` of `builtin` becomes `local`, `embed.model` is cleared, `embed.device` leaves the file, and under `<data dir>\models\` the folders the old store wrote (`.partial` and each folder that holds a `manifest.json`) are deleted, then `models` itself when it is empty; other files stay, and the log says how much was freed. `CODEWIKI_EMBED=builtin` in the environment cannot be rewritten: `embed.problem` says the built-in embedder was removed, and search is full-text alone. `cw_update::recover_and_clean` removes an old `cuda\` folder from an installation, and `uninstall.ps1` does too.
  - **Tests.** No test calls a model server. The background job takes its embedder from `ServerConfig::host` (`Host`), which `embed_job.rs` replaces with stand-ins; the route tests in `api.rs` keep `Host::default`, the process's embedder slot. Every test harness that builds a router or calls `serve`, and every test of `cw-wiki` that builds an index, first configures that slot from empty settings and no environment (`no_model_server` in `crates/cw-server/tests/api.rs`, `embed_job.rs` and `crates/cw-wiki/tests/support/`), so the slot never builds from the machine's environment. A test that chooses a server points its address at a stand-in or a closed port (`closed_port` in `api.rs`), never at a default port. `crates/cw-server/tests/embed_job.rs` is a test program of its own because it switches the process's embedder. `crates/cw-embed/tests/wire.rs` drives each provider against a stand-in server whose shapes come from the servers' own docs and source, which the file's header cites.
- **Tests.** Unit tests sit beside the code. `crates/cw-wiki/tests/` has one file per analysis plus `pipeline.rs`; the server's routes are tested in `crates/cw-server/tests/api.rs`. `explanations.rs` there covers what an agent may write. `wire.rs` in `cw-embed` drives each HTTP embedder against a stand-in server, so no API key is needed.
- **Orientation.** `obsidian/00-Architecture/` holds the generated crate dependency flow and the startup flows of `codewiki` and `codewiki-app`.

## Adding a feature

A backend feature usually touches four places: the logic in `crates/cw-wiki/src/`, a route in `crates/cw-server/src/api.rs`, a subcommand in `crates/codewiki/src/main.rs`, and a tool in `crates/codewiki-mcp/src/main.rs`. An app page is a page function that builds a `Doc` in `crates/codewiki-app/src/pages.rs` or `live.rs` (see App look), plus a palette entry in `palette.rs`. A new setting is a block in the function of its category in `settings_pages.rs`, a field in `Model` when it needs new data, and an `Action` that `run_action` or `run_settings_action` carries out.

## Commands

```
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo deny check advisories bans sources
```

Run all four before reporting work as complete.

To run fewer tests:

```
cargo test -p cw-wiki                 # one crate
cargo test -p cw-wiki --test health   # one file in crates/cw-wiki/tests/
cargo test -p codewiki-app themes::   # tests whose path contains the filter
```

To run the app:

```
cargo build -p codewiki
cargo run -p codewiki-app -- <repo> [<view>]
```

The RustRover run configurations in `.run/` do the same; `codewiki-app` builds `codewiki backend` first. `scripts\clean.ps1` keeps exactly those two dev builds and prunes every other debug artifact.

To build the package:

```
pwsh scripts\package.ps1              # dist\CodeWiki-<version>-windows-x64.zip and -setup.exe
```

After the zip, `package.ps1` builds `dist\CodeWiki-<version>-windows-x64-setup.exe` from `scripts\setup\codewiki.iss` when Inno Setup 6's `ISCC.exe` is found (on `PATH`, in `C:\Program Files (x86)\Inno Setup 6\` or in `%LOCALAPPDATA%\Programs\Inno Setup 6\`). `-NoSetup` skips it. Without ISCC it says so and still builds the zip. The setup program runs `install.ps1` from the zip's files and `uninstall.ps1` on uninstall, and is unsigned.

`package.ps1` builds with line tables and without stripping (`CARGO_PROFILE_RELEASE_DEBUG`, `CARGO_PROFILE_RELEASE_STRIP`; the profile in `Cargo.toml` stays as the Docker image needs it), so each program gets a PDB file. It copies each program and its PDB to `dist\symbols-<version>\` for Sentry and keeps them out of the zip. With `CODEWIKI_SENTRY_DSN` set, the programs carry that DSN.

## CI

`.github/workflows/` holds four workflows:

- `ci.yml` runs the four commands above, with `--locked`: format, clippy and the tests on Windows, and `cargo deny` on Linux in two legs (advisories; bans and sources). The licenses of dependencies are not checked, by the owner's decision of 2026-11-20: `deny.toml` has no list of allowed licenses, so a bare `cargo deny check` fails on every crate. The advisories leg can fail with no change in this repository, when a new advisory is published: fix the dependency, or add the advisory's ID to `ignore` in `deny.toml` with a reason. It also runs `codewiki check` on this repository and uploads the findings to code scanning; that job never fails the build.
- `security.yml` runs gitleaks over new commits. Never commit a secret, not even a test value that looks real. A confirmed false positive goes in `.gitleaksignore` by its fingerprint.
- `release.yml` and `docker.yml` run on a `v*` tag. The tag must equal `v` plus the workspace `version` in the root `Cargo.toml`. A tag publishes the Windows zip, the setup program and a `.sha256` for each as a GitHub Release, and pushes the image to GHCR. `release.yml` also builds the package, without publishing, on pushes to main and on pull requests that change `scripts/setup/**`, `package.ps1`, `install.ps1`, `uninstall.ps1` or `release.yml`. Do not push a tag unless asked. The package carries the DSN of the repository variable `SENTRY_DSN`; after the release, the programs' debug files (`dist\symbols-<version>\`, written by `package.ps1` and never put in the zip) go to the Sentry project `fly-theonlyone/codewiki` with `sentry-cli`, when the secret `SENTRY_AUTH_TOKEN` is set. The token is given to that step alone, never to the build.

Dependabot (`.github/dependabot.yml`) opens weekly update pull requests and leaves `gpui-kit` alone.

Check crate APIs against docs.rs or the crate source for the pinned version before using them. GPUI is pre-1.0 and exact-pinned; do not bump it as a side effect of other work.

## Checking the app without taking focus

Start `codewiki-app <repo> <view>` with `CODEWIKI_INSTANCE=new` in its environment (without it, the launch hands over to an app that is already running, and that one comes to the front), where `<view>` is a note name or one of `home:` (the default), `graph:`, `palette:<query>` (opened over Home), `edit:<note>`, `waiting:` (the Waiting notes page; the palette has "Show waiting notes"), `settings:` or `settings:<category>` (`appearance`, `search`, `backend`, `repositories`, `updates`, `keyboard`, `diagnostics`), `themes:`, `health:`, `contracts:` and similar. `_HOME` opens the wiki map note. Capture the window with `PrintWindow` and post input with `PostMessage`; do not bring the window to the front, and never capture the whole screen. Start it with `System.Diagnostics.ProcessStartInfo` (`UseShellExecute = false`, `CreateNoWindow = true`, the environment through `.Environment`). `Start-Process -WindowStyle Hidden` hides the GPUI window itself: there is then no window to capture or post keys to.

The window is glass over the Windows backdrop, which a capture cannot see. Set `CODEWIKI_BACKDROP=#RRGGBB` to paint an opaque color under the glass, `CODEWIKI_BACKDROP_DRIFT=1` to keep the backdrop drifting while the window is inactive, and `CODEWIKI_MOTION_SCALE=<n>` to slow every animation by `n` so that a capture can catch one half way. Closing the app's window (`WM_CLOSE`) hides it and ends nothing. To end the app and its backend, start it on `palette:Quit CodeWiki` and post Enter (`WM_KEYDOWN`, `0x0D`), or end it by force and stop its backend (`POST /v1/shutdown` with the token from `backend.json`). An app ended by force (`taskkill`, a crash) leaves its backend running; stop that one too when a check ends. Give a check its own `CODEWIKI_DATA_DIR` and `APPDATA`, so that it shares no backend, no settings and no instance with the owner's app. What needs the window brought to the front (a click on the tray icon, the tray menu, a second launch without `--tray`) is checked in the VM, not here.

## Testing a package in a clean Windows

`scripts/vm` drives a Hyper-V guest from the host: `provision.ps1` installs Windows unattended and takes the checkpoint `clean`; `provision-gpu.ps1` adds the checkpoint `clean-gpu`, the same guest with the host's graphics driver in it; `test-release.ps1` restores `clean` (or, with `-Gpu`, `clean-gpu` and attaches a share of the host's graphics card; `-VmName`, `-User`, `-Password` and `-Snapshot` name another guest, account and checkpoint), installs the newest zip in `dist\`, runs the cases and writes `report\vm-test-<date>\` (screenshots, a recording, `logs\results.json`). `Vm.ps1` holds the helpers, `record.ps1` films the screen, `guest\probe.ps1` runs inside the guest and reports what is installed and running. A run ends with a `report.md` in that folder that opens with a summary. `report\` is not in git; on the development machine `report\vm-test-2026-11-21-0.3.0\report.md` is the model. It needs the account in "Hyper-V Administrators", `oscdimg.exe` from the Windows ADK for provisioning, and `ffmpeg` for the recording.

What the first runs taught, and the scripts now assume:

- A command sent over PowerShell Direct runs elevated and without a desktop. What a user would do goes through `Invoke-GuestScript`, `Invoke-GuestExe` and `Start-GuestExe`, which use the logged-in desktop session.
- A window opened by `Start-GuestExe` has no keyboard focus. Call `Show-GuestWindow` before `Send-Keys`, or the keys go to the desktop. It also returns the window's position, which click positions are measured from.
- Never name a helper `Start-Vm` or `Stop-Vm`: PowerShell ignores case, so it replaces the Hyper-V cmdlet and calls itself.
- Hyper-V starts a guest only when all its memory is free on the host. 2048 MB is enough for a stripped image.
- Without `-Gpu` the guest has no graphics processor and Direct3D runs on the processor. The drifting backdrop once took every core there, so it now stands still on a software adapter (`backdrop.rs`). P1 measures the idle load with `Get-GuestProcessorLoad`, which asks the host; should it ever starve the guest again, the test sets motion to "reduced" to go on. Run both passes for a change to drawing or motion: they are two different user machines.
- With `-Gpu` the guest shares the host's card, which Microsoft does not support on a Windows 11 host. After a graphics driver update on the host the guest's driver copy is stale: run `provision-gpu.ps1 -Force`. A low idle load proves the card only together with a picture: on some Windows builds the guest then draws nothing at all (`Test-GuestDisplay` in `Vm.ps1` explains and checks it).
- `Show-GuestWindow` clicks the window, and that click is input: it hides any defect where the app waits for input to draw. The F2 cases start the app and leave it alone.
- A guest command that times out prints nothing. Treat empty output as a failed probe, never as "nothing is running".
- A guest account may have no password: pass `-Password ""`. PowerShell Direct then needs `LimitBlankPasswordUse = 0` under `HKLM\SYSTEM\CurrentControlSet\Control\Lsa` in the guest. The guest's folders are read from the guest (`C:\Users\Software Tester` has a space; a program path given to Task Scheduler must be quoted).
- Never take a program's window from `MainWindowHandle`. With the pointer resting where the app's close button appears, that handle is the tooltip Windows shows for the button, and every click measured from it misses. `Show-GuestWindow` and `Get-GuestWindowInfo` take the largest visible window of the process.
- A click right after its own pointer move reaches a control that has just been redrawn for the hover. Use `Send-RestedClick` (move, rest, press) for anything that might stop answering while the pointer rests on it; the title bar's buttons once did.
- Closing the app's window hides it; only Quit ends the app, and its backend with it. The next start then brings up a new backend and takes longer; `Stop-GuestApp` ends the app by force and leaves the backend. Wait longer after a real Quit. An app left hidden takes the next `Start-GuestApp`: the launch hands over to it, so state from the case before (tabs, an open editor) is still there. End the app between cases that must start clean.
- The host must have the guest's whole memory free each time the guest starts, a restart in the middle of a run included. `Start-Guest` frees memory when there is too little and tries once more.
- With `-OldZip <older package>` case U2 installs the older version and has it update itself to the package under test, which `guest\update-server.ps1` serves in the guest in GitHub's place (`CODEWIKI_UPDATE_URL`, set for the guest's user). An older package needs the workspace version and the crates' requirements on each other lowered together (`version = "0.1.0", path` in the manifests), built without `--locked`, and none of it committed. With `-ReleaseTag` case R1 downloads the published package in the guest and compares checksums; with `-RealRelease` U2 asks the real GitHub.
- With `-Hardened`, `guest\harden.ps1` turns Windows' own protection up before anything is installed: today's definitions, the cloud block level at zero tolerance, controlled folder access, network protection, every attack surface reduction rule on block, UAC on "always notify", SmartScreen on block. It excludes and allows nothing. Two of those rules judge a program by how many machines have seen it and for how long ("Block executable files from running unless they meet a prevalence, age, or trusted list criterion" and "Use advanced protection against ransomware"), and they refuse a new unsigned build: "Access is denied" for `codewiki.exe` and `codewiki-mcp.exe`. Case S3 records that right after the install and sets those two rules to audit (`harden.ps1 -Audit`), so that the cases after it can be judged; S2 lists at the end what Defender stopped. Which of the two rules speaks first differs from start to start. The rules are off unless an administrator turns them on. Only a signed build would pass them.
- With `-Plugin`, cases CC0 to CC9 test the plugin with the real Claude Code (CC9: a folder kept with `codewiki agents off` gets no wiki from a live session). Git for Windows and Claude Code are installed in the guest as their docs say, after the cases that need a Windows without git; the checkpoints stay without it. The guest gets the access token of the host's own Claude login and nothing else of it (`Copy-ClaudeLogin`): not the refresh token, because a renewal in the guest can end the login on the host, and none of the other services' tokens the same file holds. The token is never printed and is removed at the end; take no checkpoint while it is in the guest. `ENABLE_CLAUDEAI_MCP_SERVERS=false` keeps the account's own connectors out of the guest's sessions and out of the report. The plugin is installed from the installation's `plugins` folder, and one session has Claude call `get_overview`. The cases make three short requests on the account's cheapest model.
- A documented command is run in the guest as written before it is believed. README's first way to install the plugin cloned the repository, which needs git, and a clean Windows has none.
- In the palette a note can outrank a command: "logs" opened the note "Logs Module", not "Open logs folder". A case types the command's whole name.
- A checkpoint goes stale. To bring one up to date: restore it without the graphics card (Hyper-V takes no checkpoint while one is attached), run `Update-GuestWindows` in rounds with a restart between them until it says "nothing to install" (the monthly update can fail twice before it goes in), `Update-MpSignature`, shut down, rename the old checkpoint, and call `Checkpoint-VM` once: its list lags, and a second call makes two checkpoints with one name.
- A release build in a second checkout beside a running guest runs a 16 GB host out of memory. Build with the guest off.
- In PowerShell `$x = if (...) { @($one) }` hands back the one item, not an array, and a text plus an array is one text. Wrap such a value in `@(...)` where an array is needed; a rule list built without it named no rule at all.
- Cases ER1 and ER2 test error reports. ER1 turns the switch on through its file and sends a test report and a panic with `codewiki sentry-test`; ER2 photographs the switch in Settings. A package built without `CODEWIKI_SENTRY_DSN` refuses with the switch on too, which ER1 records as a note. Whether the reports arrived, and with readable stack frames (the debug files must be uploaded first), is read in Sentry afterwards.
- A script sent to the guest runs in Windows PowerShell 5.1 and prints nothing at all when it does not parse. `"$what: ..."` does not parse there: it reads as a variable on a drive. Write `"${what}: ..."`. A case with empty output is a script that never ran.
- The host's graphics driver changes without notice (Windows Update did it in the middle of a day's work). With `-Gpu -RefreshGpuDriver` the run copies the host's driver into the guest when the checkpoint holds an older one, and leaves the checkpoint as it is; `provision-gpu.ps1 -Force` is what retakes the checkpoint.
- The script checks exit codes, files and processes. What a page looks like is known only from reading the screenshots; read every one a report cites.
- Windows PowerShell 5.1 has two JSON traps that the first run of the 0.3.0 cases hit. `ConvertTo-Json` writes an array that came out of a function's pipeline as `{"value": [...], "Count": n}`: cast it (`[double[]](Get-Vector ...)`) before it goes into the object. `@(... | ConvertFrom-Json)` on a JSON array gives one item, the whole array, so a filter over it matches every element: put the parsed value in a variable first, then filter it.
- With `-Setup <CodeWiki-version-windows-x64-setup.exe>` (default: the one beside the zip, named for the same version, else the newest there; without one the cases do not run, and a release run always gives it) cases IS1 to IS8 test the setup program, each from no installation and back to none: IS1 silent install (`/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /LOG`, files, PATH, shortcut, Apps entry, `codewiki --version`, start from the shortcut), IS2 uninstall through the entry's `QuietUninstallString` with the app running (data and settings stay), IS3 uninstall refused while `codewiki-app.exe` is held open (a `FileShare.None` handle in a background PowerShell), IS4 the wizard by mouse (Install and Finish found by their text among the wizard's child windows, read with `WM_GETTEXT`: on the first run UI Automation found no button in the wizard), IS5 over an `install.cmd` installation with the app running, IS6 a failing install (exit 7, `CodeWiki could not be installed` in the log, no Apps entry), IS7 another folder refused (`/DIR=C:\Users\Public\cwvm-elsewhere`: exit 7, `CodeWiki installs only to` in the log, no programs there or in the default folder, no Apps entry), IS8 the setup program over its own installation (second exit 0, the `PATH` entry once, one Apps entry with the version, `codewiki --version` answers; then the uninstall from the entry exits 0 and leaves nothing). U2 also checks that the update moves the Apps entry's `DisplayVersion`; its old package must hold that code. The uninstaller starts a copy of itself and may return early, so a case waits for the uninstaller processes to end before it reads the files; the exit code it returns is still the copy's (IS3's aborted uninstall gives 1). Setup logs go to `C:\Users\Public` in the guest, a path without spaces. Run `-Only IS1,IS2,IS3,IS4,IS5,IS6,IS7,IS8`.
- Cases added for 0.3.0: AV1 (the agent view), Z1 (Ctrl+wheel zoom: it holds Ctrl on the VM's keyboard device and turns the VM's wheel, and reads `zoom.txt`), LR1 ("Open the last repository", turned on through `open_last.txt`), DV1 (the diagram viewer, on a three-crate workspace it builds in the guest, since cw-core has no Mermaid diagram), D4 (the three note-writing MCP tools over stdio, `guest\mcp-write.ps1`), U3 (after U2: what 0.3.0 cleans up from 0.2.0; U2 seeds the old writer sections of `settings.json` and a `cuda` folder holding `codewiki-embed-cuda.exe`, without which the app rightly leaves the folder alone), SE1 and SE2 (`guest\embed-server.ps1`, a stand-in OpenAI-style server on port 9931 chosen as `llamacpp`), and the real embedding servers OL1 to OL5, LC1 to LC3, LS1 to LS3, LM1 to LM3 and MR1 to MR3 (below).

## Releasing

The `qingyi:ship-release` skill runs a release and reads its facts from this section.

- **Checks.** The four commands under Commands.
- **Version.** `version` in the root `Cargo.toml`, the `version = "<old>", path` requirements in `crates/*/Cargo.toml`, `plugins/claude-code/.claude-plugin/plugin.json` and `plugins/codex/.codex-plugin/plugin.json`; `crates/codewiki/tests/plugins.rs` fails when a plugin is missed. Then run `cargo check --workspace` once without `--locked`: it rewrites `Cargo.lock`, which the package build and CI then hold to. Commit as `chore(release)`.
- **Previous package.** Before the bump: `gh release download v<previous> --repo Fly-onlyone/CodeWiki --pattern "*.zip*" --dir dist\old`, then check it against its `.sha256`. A package built before the bump has the old version's name and replaces the zip in `dist\`.
- **Package.** `pwsh scripts\package.ps1`.
- **Publish.** After the push, wait for `ci.yml` and `security.yml`. The tag `v<version>` starts `release.yml` and `docker.yml`; `gh release view v<version>` then shows four files: the zip, the setup program and a `.sha256` for each.
- **Docs.** `ROADMAP.md` (date, crate and test counts, what is now verified, the VM run), `README.md` (status line, features), this file (what a later agent must know about the new parts), and the wiki: `cargo run -p codewiki -- update` at the repository root, with `obsidian/` committed as `docs(wiki)`.
- **Clean-up.** `pwsh scripts\clean.ps1`.

## App look

The look lives in `crates/codewiki-app/src/`: `glass.rs` (how opaque each surface is), `reading.rs` (note typography), `icons.rs`, `motion.rs` (whether things move), `backdrop.rs`, `constellation.rs` and the `mui/` module.

The backdrop has two layers under the glass. The color glow (`backdrop.rs`, the shapes) lies behind everything, and `glass` fits the chrome's opacity to its `STRENGTH`, so it stays faint. The sky (`constellation.rs`: a fixed graph of notes and links, its pulses and their schedule) is drawn only in the clear margins beside a page's reading column, which the app reports to the shell through `backdrop::Margins`: a margin holds no text, so its glass (`Levels::margin`) can be clear and the sky strong without a contrast limit. Never draw the sky behind the chrome or the column. A page gets margins from `glass::reading_surface` when it has a centred column (notes, generated pages, Home) and room for them; the bars above the page then carry the pane's surface themselves. Pulses come more often while a wiki is written: `AppView::tell_backdrop` sets `backdrop::set_writing` from the app's own sync and from `updating` in `/v1/status`. "Background graph" (Settings → Appearance, `backdrop.txt`) turns off the glow, the sky and the clear margins.

`mui/` holds the controls, drawn to Material UI's measurements with the TradingAgent theme's changes; where the two differ, TradingAgent wins. Draw a control with a `mui` component, not with a gpui-kit one and not by hand. A number copied from MUI or TradingAgent names its source file in a comment. Springs and entrances come from `mui/motion.rs`; do not write a duration or a spring anywhere else. GPUI cannot scale an element, blur what is behind one, or clip to rounded corners; `mui/mod.rs` and `mui/ripple.rs` say how each is worked around.

The whole app zooms (Ctrl+wheel, Ctrl+= / Ctrl+- / Ctrl+0, the palette, Settings → Appearance; `zoom.rs`). GPUI cannot change a window's scale, so a size written as an `f32` is in design units and `crate::zoom::px` turns it into GPUI's pixels at the current zoom; the app's modules import it in place of GPUI's `px`, and a pixel value turned back into a number (`width / px(1.)`) is in design units too. `zoom::sync_theme` scales the theme's font sizes and radii, which moves the rem and with it every gpui-kit control. GPUI's own `px` is for what keeps the screen's pixels at every zoom (the window's measures, the backdrop's shapes, the hairline); clippy refuses it elsewhere (`crates/codewiki-app/clippy.toml`), and each such use carries an `#[allow]` that says why. Never mix the two in one expression: `px(x / gpui_kit::px(1.))` zooms twice. The title bar stays at 100%, as a browser's does: the shell builds it in `zoom::unscaled` and lays it out in `zoom::FixedRem`. The shell takes Ctrl+wheel in the capture phase, before anything under the pointer can scroll or zoom itself. Mermaid diagrams in a note keep their size.

A note narrows a wide diagram to its column, where a sequence of twelve parts is drawn at 28% and cannot be read. The image element is gpui-base's, so the note cannot scroll it or draw it larger. A drawn diagram is therefore a link (`markdown::OPEN_DIAGRAM_SCHEME`, written by `prepare_note_with`), and a click opens the diagram viewer over the window (`AppView::open_diagram` and `diagram_viewer_view` in `main.rs`): fitted, and never above its natural size. The wheel zooms about the pointer, a drag moves the diagram, `+`, `-`, `0` (fit) and `1` (natural size) do the same as the header's buttons, and Escape, the close button or a click outside closes it. `diagram_view.rs` holds the geometry and its tests; it looks at the diagram through `graph::Camera`, with limits of its own. The viewer shows the note's picture at once and has the diagram drawn again at twice the pixels off the UI thread (`cw_mermaid::render_png_scaled`), so that it stays sharp; one such picture is kept, and the one it replaces is handed back to GPUI with `Image::remove_asset`, because each is tens of megabytes decoded. The viewer's sizes go through `zoom::px`, so it follows the app's zoom, and Ctrl+wheel stays the app's zoom inside it. Closing only clears a flag: `render` gives the focus back, since not every way to close has the window.

A generated page is a `Doc` (`doc.rs`): a page function in `pages.rs` or `live.rs` builds it from backend data, `doc_view.rs` draws it, and each link, row and button carries an `Action` that `AppView::run_action` carries out. Do not build a page as Markdown; only notes are Markdown. A page function has a test that reads its `Doc`.

An `Action::Note` names a note by its whole vault path, `.md` included, or by its bare name: the backend's `find_entry` (`cw-wiki/src/query.rs`) knows those two and nothing else, so a folder path without `.md` is "not found".

The toolbar's search box suggests while it is typed in. `suggest.rs` holds the list's state and keys; `mui::autocomplete::Listbox` draws it under the box. Each change of the text replaces the lookup before it (dropping the task cancels it); the lookup waits `suggest::PAUSE` and asks `GET /v1/repos/{id}/search?mode=text`, which searches words only and never calls the embedder. It does not go through `AppView::run`, so it sets no busy line and clears no error. The box keeps the focus: the root's capture handlers give Up, Down and Escape to the open list, as they do for the palette, and Enter opens the highlighted hit or else runs the full search. A row's press never moves the focus (`mui::base`), so the list chooses a row on click and closes when the box loses the focus. `live::hit_target` and `live::hit_groups` turn a hit into what it opens, for the list and the Search page alike; `live::plain_snippet` turns a note's snippet into one line of plain text.

The Settings page (`Page::Settings(Category)`) fills the window, as Home does. `settings.rs` names its categories and the fields that are typed; `settings_pages.rs` builds the `Doc` of each category from a `Model`; `settings_view.rs` holds its state and draws the frame. Its `Doc` is drawn by the app's view, with `doc_view::column`, and not by the cached page view: a text input and the list of a select take their events through the view that owns them, as the search box and the theme menu do. So `Block::Switch`, `Select`, `Field` and `Secret` work only on a page drawn that way. A text input needs a window to be made and must outlive the frames, so the app's view makes one for each `FieldId` at its start. A change is applied when it is made: a field saves itself on Enter or when the focus leaves it, and also when its page is left, because the field is gone by then and reports nothing. The measures of the layout that are a matter of taste are in `settings_layout.rs`; numbers copied from MUI stay in `mui/`.

A module that brings in the kit with `use gpui_kit::*` must not write `use super::*` in its tests: the glob carries GPUI's own `test` attribute, which then stands in for the standard one and fails with "recursion limit reached".

The title bar is drawn by the shell (`backdrop.rs`), in every frame, not by the app's view, which the shell draws from its cache. GPUI does not keep the window control areas of a cached view, so a title bar inside one has dead minimize, maximize and close buttons and cannot drag the window. Keep anything that calls `window_control_area` out of a cached view.

A `cx.notify()` made while a frame is being drawn (in `render`, or a canvas callback) marks the view but asks for no new frame, so the change waits for the next input. From such code, call `doc_view::notify_after_draw`. Under reduced motion, pages once stayed blank until the pointer moved because of this.

Icons are Material Icons, as SVG files in `crates/codewiki-app/icons/`. Every icon the app draws is a constant in `icons.rs`; a file that is not listed there is not embedded. A new palette command needs an arm in `icons::for_command`. A text color added to a CodeWiki theme must pass the contrast test in `themes.rs`, which checks it on the page and on a card.

Color comes from the active theme, never from a hex value in code, so every theme shows its own hue. Chrome surfaces (title bar, sidebar, toolbar, tab bar, details) are filled with `glass::tinted` and the reading pane with `glass::tinted_pane`; both mix in 6% of the theme's primary color (`CHROME_TINT`, `PANE_TINT` in `glass.rs`). Section labels are in the theme's link color. In notes (`reading.rs`), H1 to H3 take the link, magenta and cyan colors, and list markers, inline code, code blocks, table heads and quotes are tinted; body text stays neutral. A sidebar or toolbar icon takes its color from `icons::hue`, and an icon with no hue there stays neutral. Every theme except CodeWiki's own is redrawn on the CodeWiki set's levels when it is applied (`standard.rs`): each color role takes the lightness and saturation the CodeWiki themes of the same mode give it, in the theme's own hues, and text is nudged until it reads. Syntax colors are left alone. The text colors of every bundled theme must reach WCAG AA on the page, on a card and on the tinted page, and icon hues 3:1 (tests in `themes.rs` and `standard.rs`); a change to `codewiki.json` that breaks this is fixed in the colors, not in the tests. `glass` fits the chrome's opacity to the foreground, muted and link colors on the tinted surface, so a weak text color makes the chrome denser rather than unreadable.
