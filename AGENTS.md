# CodeWiki — agent instructions

CodeWiki is a Windows-only native desktop app plus a Rust backend that generates and maintains a codebase wiki (an Obsidian vault at `<repo>/obsidian/`) for humans and coding agents. `ROADMAP.md` records what is built and what is verified.

## Hard rules

- **No WebView.** The UI is native Rust on GPUI (`gpui-kit`). Do not add a browser, WebView2 or Electron dependency.
- **The app talks HTTP only.** `codewiki-app` gets all data from the backend through `cw-client`. It may link `cw-illustrate`, `cw-mermaid` and `openui-lang` to draw, never the index, parser or wiki crates. Three exceptions concern the app itself: it links `cw-update` to ask GitHub for a newer release and to replace its programs, `cw-telemetry` to send its own error reports, and `cw-core` to read and write `agents-off.json` (`cw_core::agents_off`), the list of folders kept from coding agents, and `auto-explain.txt` and `auto-explain-count.txt` (`cw_core::auto_explain`), the switch for auto explaining and how many notes it explains. All are settings of the agents on this machine and not of a backend.
- **Error reports are opt-in and scrubbed.** Nothing goes to Sentry unless `SENTRY_DSN` is set or the user turned on "Send error reports" in a build that carries a DSN. Never add a field to a report that the logs may not hold, and never weaken `cw_telemetry::scrub`.
- **Never overwrite a human-edited note.** Changes to such notes go through the proposal queue. One exception: a note whose subject is gone from the repository describes nothing, and may be deleted, but only where git holds it as it is, and for a note its owner wrote by hand only after the owner approved it (see "Notes of code that is gone").
- **The index is a cache.** Everything in it must be rebuildable from the repository and the vault. Bump `SCHEMA_VERSION` in `crates/cw-index/src/schema.rs` on any schema change; old indexes are dropped and rebuilt.
- **Keep builds small.** Do not loosen the `[profile.dev]` settings in the root `Cargo.toml`; debug builds once reached 44 GB. Run `pwsh scripts\clean.ps1` after long sessions; it keeps what the `codewiki-app` run configuration builds, so starting the app afterwards compiles nothing, and `-All` removes everything.
- **The programs must run on a clean Windows.** `.cargo/config.toml` links the C runtime statically; without it they need `vcruntime140.dll`, which a clean machine may not have. A program the app starts in the background is started with `CREATE_NO_WINDOW` (`crates/cw-client/src/lib.rs`), or Windows opens a terminal window for it. This machine has the runtime and a graphics card, so neither failure shows here; `scripts/vm` is where they show.

## How the parts connect

- **Who opens the index.** The CLI and `codewiki serve` (`cw-server`) open the index directly. The app and the MCP bridge never do: they call `cw_client::Backend::connect` in `crates/cw-client/src/lib.rs`, which uses the first of these that works:
  1. `CODEWIKI_URL` with `CODEWIKI_TOKEN`.
  2. The backend saved in `remote.json` in the data directory, while it is in use (`crates/cw-client/src/remote.rs`). One that does not answer is an error: `connect` never falls back to a local backend by itself, because one started in its place would show other wikis, or none. Only `cw_client::use_local` goes back, and it keeps the address and token.
  3. The URL and token in `backend.json` in the data directory, when `/v1/health` answers.
  4. A new `codewiki serve`, started from the binary beside the caller or from `PATH`.

  Steps 1 to 3 are `Backend::find`, which starts nothing and never deletes `backend.json`: it answers `Ok(None)` when no backend is named and none answers. `connect` is `find` plus step 4 (`start`). A caller that must not start a backend, such as the app's probes (see "Reconnect" below), calls `find`.

  `Backend::origin` says which of these it was. The app and the MCP bridge both follow `remote.json`, so an agent and the app read the same wikis.

  The backend ends with the app, and the app ends on Quit, not when its window closes (see "The tray" below). On Quit the app asks the local backend it uses to stop (`POST /v1/shutdown`), whoever started it, and does not wait. A backend named by `CODEWIKI_URL` or saved in `remote.json` is left alone (`cw_client::uses_remote`). The backend finishes the requests it is running, an update of a wiki included, then exits; an agent's MCP bridge that shared it starts a new one on its next call. Quit is refused while a note has unsaved edits (`AppView::quit` in `main.rs`).

  A backend started before a rebuild keeps serving the old code, for as long as something keeps it running (the CLI's `serve`, an MCP bridge, an app hidden in the tray, an app ended by force). Stop it after changing a backend crate (`POST /v1/shutdown` with the token, or end the process). A rebuild keeps the version, so `connect` cannot tell; it does replace a local backend whose version is older than the client's, which is what an update leaves behind, and never a newer one. A backend that ends before it answers is reported at once; the app then offers "Try again", and the MCP bridge tries again on its next call. The bridge also drops a backend it was using once that one stops answering, and connects anew.
- **The spawn guard.** `cw-client` keeps the child it started last (`STARTS` in `lib.rs`). A start is refused while that child runs and `backend.json` has not yet named its pid: it may be starting, however long a cold disk or a virus scan takes, and a second one would race it for `backend.json`. `start` then waits for it, up to `STARTUP_TIMEOUT`. Once `backend.json` names the child's pid, it has listened; if it does not answer now it is ending or hung, and a new backend may start beside it (a backend that ends deletes `backend.json` only while the file is its own). `backend.json` is deleted only when a new backend is spawned. `cw_client::hold_starts(true)` stops every start in the process: the app sets it while an update replaces the programs, because a backend started then would run the program being replaced, and clears it when the update fails.
- **Reconnect.** The app keeps trying to reach its backend (`crates/codewiki-app/src/connection.rs`, pure logic with tests; the glue is `supervise`, `reach` and `take_attempt` in `main.rs`). At startup the offline page probes with `Backend::find` only: a start was already tried, and the page says "CodeWiki keeps trying to connect.". Mid-session, a loss counts after 2 silent status polls in a row (`SILENT_POLLS`; a poll that is answered, or not asked, resets the count), and the banner "Backend not reachable, reconnecting…" shows. A local backend then gets one full attempt (`Backend::connect`, which may start a backend), then probes; a remote backend (`CODEWIKI_URL` or `remote.json`) gets probes only, so the app never starts a backend in the place of one that lives elsewhere. Waits grow 5, 10, 20, 30, 30 s (`BACKEND_FIRST`, `BACKEND_CAP`); an answer to a status poll during a loss makes the next attempt due at once. One attempt runs at a time, a sequence number (`Sequence`) drops the result of an attempt that "Try again" or a switch of backend overtook, and none starts while an update installs. The toasts are "Connected" (at startup) and "Reconnected" (mid-session, which also reloads the open repository quietly, or goes Home when it is not on that backend).
- **Updates.** `cw-update` checks GitHub's latest release (`CODEWIKI_UPDATE_URL` replaces the API address in tests), downloads the zip into `<install>\.update`, verifies its `.sha256`, runs the new `codewiki.exe --version`, has the app stop the backend, then renames each installed entry to `<name>.old` and moves the new one in. Windows lets a running program be renamed but not replaced, so the app and an agent's bridge keep running from the `.old` file. Every move is written to `.update\swap.json` before it is made and undone on the first failure; `recover_and_clean`, at the app's start, undoes a swap cut short and deletes the `.old` files no longer in use. After a swap the app writes the new version into `DisplayVersion` of the Settings → Apps entry, when that entry exists (the setup program makes it; `install.cmd` does not). Only an installation made by `install.ps1` updates itself (`uninstall.ps1` beside the programs, `install.ps1` not). The app's part is `crates/codewiki-app/src/update.rs`; the check runs once a day (`update_checked.txt` in the settings folder) unless `update_check.txt` says `off`: at the start, and every hour a running app looks whether the day is over, since an app in the tray runs for weeks. It only ever offers. Before it starts the new version, the app gives up its place as the running instance (`instance::release`), or the new app would hand over to the one that is ending.
- **Where state lives.** The index and the backend's state are in `cw_core::paths::data_dir()`: `CODEWIKI_DATA_DIR` when set, otherwise `%LOCALAPPDATA%\CodeWiki`. `auto-explain.txt` is there too (`on` or `off`; a missing file means on, anything else or an unreadable file means off; the app writes it, and `codewiki hook session-start` and the app read it), and so is `auto-explain-count.txt` (a positive number or `all`, `Count`; a missing, unreadable or other file means 20, `auto_explain::DEFAULT`; written and read the same way). Two settings files are there too: `settings.json`, which only the backend writes, and `remote.json`, which only `cw-client` writes, so neither program can overwrite the other's change. The vault is `<repo>/obsidian/`. The app's settings (`theme.txt`, `motion.txt`, `zoom.txt`, `log_level.txt`, `last_repo.txt`, `update_check.txt`, `update_checked.txt`, `tray_hint.txt`, `open_last.txt`, `backdrop.txt`, and `recent_repos.txt`, which holds one folder per line, newest first) are in `%APPDATA%\CodeWiki` (`prefs.rs`; the app deletes the old `model_hint.txt` at its start), and so are the two files of the running instance (`instance-<key>.lock` and `.txt`). `error_reports.txt` is there too: the app writes it, and every program that reports reads it itself (`cw_telemetry::consent`). Two things are outside it, in the user's registry, and `uninstall.ps1` removes both: "Start with Windows" is the value `CodeWiki` under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` (`autostart.rs`; the value is the whole setting), and the key that names the app's notifications and gives them their icon (see "Notifications") is `HKCU\Software\Classes\AppUserModelId\CodeWiki.App`. A debug build (`cw_core::DEV_BUILD`, `cfg!(debug_assertions)`) uses `CodeWiki-Dev` in place of `CodeWiki` under both folders (`cw_core::paths::APP_FOLDER`), calls itself "CodeWiki Dev" in its title bar, sidebar and tray (`cw_core::APP_NAME`), and shows its notifications as `CodeWiki.App.Dev`. A run from the sources therefore never finds, uses or stops the backend of an installed CodeWiki, and never reads its index or settings; it starts with no repositories and the default embedder. The variables still win over both folders. `cw-client` passes its data folder (`CODEWIKI_DATA_DIR`) to a backend it starts, so a release `codewiki` found on `PATH` writes `backend.json` where the caller waits for it.
- **Logs.** Every program logs through the `log` crate and the one logger `cw_core::logs::init` installs: each record goes to `<name>.log` and to standard error, and a file over 1 MB is moved aside to `<name>.old.log`. The folder is `logs\` under the data directory (`CodeWiki-Dev\logs\` for a debug build), or `CODEWIKI_LOG_DIR` (a relative path is taken from the working folder). The RustRover `codewiki-app` configurations set it to `logs`, so a run from them writes to `<repo>\logs\`, which git ignores. The app writes `app.log`, GPUI's records and every panic included. `codewiki serve` writes `backend.log`: its start, with the writer and embedder in use; failed, refused and slow requests; each step of a sync with its time, and a summary; failed LLM calls; its stop. The MCP bridge writes `mcp.log`. Other CLI commands print warnings only, and the session-start hook prints nothing. The app also says when a page has been drawn with its data: `page drawn: <kind>` under the log target `page`, once for each page, with `(asked <view>)` on the page that answers a launch, and `page filled: diagrams` or `page filled: models` for what arrives later (`crates/codewiki-app/src/ready.rs`, `AppView::announce_page`). The line names a note, never a search, a palette query or a file's path, and `cw-telemetry` keeps the target out of the error reports. A check waits for this line instead of a fixed time (`Wait-AppPage` in `scripts/vm/test-release.ps1`). `CODEWIKI_LOG=debug` keeps more, such as every request and each LLM call. The app's level can also be chosen in Settings → Diagnostics: it is kept in `log_level.txt`, applied at once with `logs::set_level`, and the variable wins over it. `cw-client` passes its log folder to a backend it starts and leaves the backend's standard error unconnected, because a pipe nobody reads any more would stall it. A backend that was already running keeps logging where it was started. Never log a token, a key, a query string, a prompt, an LLM answer or note text. "Open logs folder" (palette, Settings, the page shown when the backend is not reachable) shows the folder in Explorer. Read the logs before guessing why something did not start.
- **Error reports.** The app, `codewiki serve` and the MCP bridge start their log with `cw_telemetry::init` instead of `cw_core::logs::init`. It installs the same file logger, wrapped in Sentry's when reports are on: an Error record becomes a report, Info and Warn records become its breadcrumbs, and a panic is reported by Sentry's own hook with its backtrace (the `panic` record is left out, so it is not reported twice). Other CLI commands and the session-start hook never report.
  - **When.** `SENTRY_DSN` in the environment turns reports on for that process and the ones it starts. Otherwise a build made with `CODEWIKI_SENTRY_DSN` set carries that DSN (the release workflow sets it from the repository variable `SENTRY_DSN`), and reports only while `error_reports.txt` says `on`: Settings → Diagnostics → "Send error reports", off by default. Turning it on applies from each program's next start; turning it off applies at once, because every report reads the file again (at most every five seconds). A dev build without either never starts the SDK.
  - **What.** `cw_telemetry::scrub` runs on every event and breadcrumb: no host name, no user, no query string, headers, cookies or body of a request, every absolute Windows path replaced by `<path>`, a loaded program named by its file name alone. Names are not scrubbed: a log line that names a repository, a note or a remote backend's address reaches Sentry as it is, and README and the Settings page say so. The project has "Prevent Storing of IP Addresses" on and the Advanced Data Scrubbing rule `[Remove] [Anything] from [$user.geo.**]`. Sentry's Relay looks up a city and country from the address a report arrives from before it drops that address, and the Rust SDK (0.49) cannot ask it not to (`sdk.settings.infer_ip` is not in it, and Relay's lookup ignores that setting anyway), so the rule removes them. README and the Settings page promise that Sentry keeps neither the address nor its city and country: both are project settings in Sentry, not code, and must stay on. Each report is tagged `program` (`app`, `backend`, `mcp`), its release is `codewiki@<version>`, its environment `SENTRY_ENVIRONMENT` or `development`/`production` by build.
  - **Traces.** The backend traces a request (`trace_request` in `crates/cw-server/src/api.rs`) as a transaction named by method and route (`GET /v1/repos/{id}/search`), with no request data: Sentry's own tower layer would send the query string, and the SDK has no hook that scrubs transactions. `/v1/health` and `/v1/status`, which clients poll, are not traced. `SENTRY_TRACES_SAMPLE_RATE` sets the share (0.1 by default). There is no profiling: the Rust SDK has none.
  - **Check.** `codewiki sentry-test` (hidden) sends one test report, `--panic` a panic; both refuse when reports are off.
- **The tray.** Closing the window (the X, Alt+F4) hides it; the app stays, with an icon in the notification area (`tray.rs`, drawn by the `tray-icon` crate). A click on the icon shows the window, a right click opens a menu, and Quit, there and in the palette, ends the app. The tooltip and the menu's first rows say what the app is doing: the open repository, whether a wiki is being updated, and when an agent's MCP bridge last called. The app does not know the last two by itself. It asks the backend every 5 seconds (`GET /v1/status`, `cw-server/src/activity.rs`): the route lists the updates that are running, whoever started them, and the time of the last request that carried `x-codewiki-client: mcp`, which only the bridge sends (`Backend::with_client`). The route also reports `notes_rev`, a counter the backend raises whenever a vault or a claim changes (a claim that runs out counts); the app refetches the waiting list when it moves (`take_status` and `load_waiting` in `crates/codewiki-app/src/main.rs`), which keeps the toolbar's "To explain (N)" and the Waiting notes page current. `status.rs` puts that into words; `tray::rows` is the menu as plain data, and both are tested without a tray. The menu keeps its shape and changes its rows in place, because a menu rebuilt while open closes under the pointer. Without a tray icon (Windows refused one) closing the window ends the app, as it did before.

  Three rules keep this from breaking GPUI:
  1. A click on the icon or a menu row arrives in a window procedure, and a second launch on another thread. Neither may touch the app. They send an `Event` through a channel, and one task of the app's view carries each out (`AppView::listen`).
  2. Hiding and showing the window (`win32::hide`, `win32::show`) make Windows call back into GPUI before they return. They are called only in that task, between two updates, never inside one.
  3. A window that was never shown (`--tray`) is first shown by `activate_window`, which also puts it in its place; `ShowWindow` before that would show it where Windows puts a new window.

  `win32.rs` is the only module of the app with `unsafe` code. Keep every Win32 call of the app there. The workspace has one more such module, `cw_core::secret`, for the Data Protection API. Every `unsafe` block says why it is sound in a `// SAFETY:` comment above it; clippy (`undocumented_unsafe_blocks`) and `codewiki check` both report one without.
- **Notifications.** Everything the app tells the user goes through `AppView::notify_user` with a `toasts::Notice` (`toasts.rs`: a key, a tone, a `topic`, a title, an optional body, an optional action, and `throttle`). The `Topic` picks the icon in front of the title (`Topic::icon`): `Backend` is `icons::CONNECTED` (`cloud-done`), `EmbedServer` is the icon of Settings → Semantic search, `Review` is `icons::REVIEW`, and `App` (the tray hint, which only goes to Windows) is `icons::INFO` and is never drawn; the tone only colors it. While the window is on screen the notice is a MUI snackbar at the bottom right (`mui/snackbar.rs`: a header row with the logo, the app's name muted (`cw_core::APP_NAME`, the one Windows shows above its notifications) and the close button, above a row with the tinted topic icon, the title and the action), at most 3 at once (`MAX_SHOWN`), each held for `TOAST_HOLD` (6 s); a notice replaces a toast with the same key. While the window is hidden or minimized (`window_on_screen`) it is a Windows notification instead (`cx.set_app_identity`, called once, just before the first one). Before that, `identity::register` (`identity.rs`) writes `DisplayName` and `IconUri` under `HKCU\Software\Classes\AppUserModelId\CodeWiki.App`, with `IconUri` naming `notification-icon.png` in the data folder, which it writes from the embedded logo; a value or file already right is left alone, and a failure is logged and never stops the notification. A debug build has its own id, `CodeWiki.App.Dev` (`APP_IDENTITY` in `main.rs`), its own name, "CodeWiki Dev", and its own `notification-icon.png` in its own data folder, so it never changes what an installed copy shows. `scripts/uninstall.ps1` removes the key and the icon file. A click on a notification or on a toast's action reaches `Toasts::route`, which gives the `Action` to run (`Action::OpenReview(repo id)` for "Open review"). A notice with `throttle`, which only the news of new reviews has, goes to Windows at most once in `SYSTEM_GAP` (60 s) per key; a newer one waits in its place. No other notice is held. The click on a notification and the focus on a second launch need a real desktop: check them in the VM.
- **Review.** `Page::Review` shows the queue (`review.rs`, pure logic; `review_view.rs`) beside the open proposal. The toolbar button "Review (N)", the palette command "Review", the start view `review:` and `Action::OpenReview` open it. Selection is by click, Ctrl, Shift and the check boxes; the buttons act on the checked rows, else on the open proposal. One proposal goes through `POST /v1/repos/{id}/proposals/{pid}/approve` or `reject`; several go through `POST /v1/repos/{id}/proposals/decide` (`Backend::decide_proposals`). The body is `{"decision": "approve" | "reject", "ids": [...]}`. The answer is 200 with `results`, one `{id, ok, note_path | error}` per id in order, because a proposal that cannot be decided does not stop the others; an empty `ids` or another decision is 400. The handler takes the write lock once and runs one index pass after the approvals (`cw_wiki::explanations::decide_all`). A backend without the route answers 404 or 405, which the client turns into "this backend cannot decide several proposals at once; update it". A retire proposal (`Kind::Retire`) lists its notes above its text, each with a check box (`review_retire` in `review_view.rs`): an unticked note is kept as history, the Approve button says how many go and how many stay (`review::retire_label`), and the approval goes by the proposal's own route with `keep`, also when other proposals are decided with it. After a decision the next proposal opens. After an approval, the written notes are dropped from the history of every tab and the tabs that show one reload it (`forget_written_notes`). The batch has no MCP tool and no CLI command: decisions stay with a person.
- **News of new reviews.** `GET /v1/status` has `proposals: {repo id: count}` (`crates/cw-server/src/pending.rs`). The status must never fail or stall because of it. Counting reads every repository's proposals, so it runs in the background, one count at a time, and the route waits for it at most 1 s (`WAIT`; the app takes a status slower than 3 s for a lost backend). An answer holds only the repositories counted fresh, after the question was asked; one whose folder is gone or whose vault cannot be read is left out. The field is always present. A client must keep the counts of repositories an answer leaves out (`review::take_counts`), and `status::Backend.proposals` is `None` for an older backend. The app also records the count of each queue it loads itself (`review::loaded`), so its own Sync raises no notice. A rise gives "N new reviews in <repo>" with "Open review" (`review::rise_notice`, key `review:<repo id>`); rises that come while that notice is still live add up (`review::Told`, `Toasts::live`).
- **One app per program.** Starting the app while it runs hands what the launch was asked to open to the running app, which shows its window, and the launch ends (`instance.rs`: a lock file the running app holds, and a line of JSON to a local port). "The same app" is the same program file, so an installed copy and a development build stay apart. `CODEWIKI_INSTANCE=new` starts a separate app whatever is running; a check or a test that must not bring another window to the front sets it. A launch that can neither take the lock nor reach the running app runs by itself after ten seconds: the app never refuses to start.
- **Which repository the app opens.** The command line is `codewiki-app [--tray] [<folder> [<view>]]` (`startup.rs`); a flag may stand anywhere and is never taken for a folder. `--tray` starts with no window on screen, as Windows starts the app at sign-in. The first of these that applies:
  1. The first argument that is not a flag.
  2. The working folder, only when it holds `.git` or a CodeWiki vault.
  3. The repository opened last.
  4. The newest repository in the recent list that is still registered.

  `startup.rs` checks the first three; `connect` in `main.rs` falls back to the fourth.

  Whatever opens, the app starts on Home (`live::home_page`, `Page::Home`), unless "Open the last repository" is on (Settings → Appearance → Startup, `open_last.txt`, off by default): it then starts on the wiki map of the repository it opened, and on Home still when that one has no wiki. The view `home:` is always Home. Home has "Open folder…" and lists every registered repository, the most recently opened first. Once a project has been opened, a search field sits above "Open folder…" (`Block::Search`). It has the focus when Home opens, and as it is typed in it suggests up to 8 projects opened before: those whose name holds the text, then those with a folder name, or a word in one, that starts with it (`live::recent_matches`, `path_matches`; a query holding `\` or `/` matches anywhere in the path). The shell draws the page, so the field is a `doc_view::SearchSlot` that the app owns, and its Escape, Up and Down reach the app through the slot's `on_key`, not through the app's own key handlers. The toolbar's Open recent button, after Back, lists up to 8 projects opened before, without the open one, then "Open folder…" (`recent_menu_entries`). Home fills the window: no sidebar, toolbar, tabs or details pane (`fills_window` in `main.rs`). The same goes for the pages shown before a repository has loaded. A second argument naming a view or note starts the app there instead, in a repository that has a wiki; one without lands on Home, which offers to sync it. A second launch that names a folder or a view opens it in the running app.

  Never let a folder the user did not choose be registered: the backend would index all of it.
- **Repositories whose folders are gone.** `GET /v1/repos` reports for each repository whether its folder still exists (`present`). The backend checks this, because the paths are on its machine. The app never forgets one by itself: a folder can be away for a while (a drive that is not plugged in, a share that is offline). Home lists such a repository under "Folder not found" with a Remove button, and only that button deletes it (`Action::ForgetRepo`, `DELETE /v1/repos/{id}`). The deletion forgets the repository only. The index files stay, and opening the folder again restores it under the same id.
- **Linked worktrees.** A linked git worktree is one more copy of a repository, most often made by a coding agent for one task, and an agent's first tool call there registers it (`Backend::repo_id` in `crates/cw-client/src/lib.rs`). It is no project. `repos::add` (`crates/cw-server/src/repos.rs`) records the id of its main checkout in `worktree_of` (`cw_wiki::git::main_checkout`), `GET /v1/repos` lists the field, and Home leaves such an entry out unless it is the open one, which says whose worktree it is; the row of its repository says how many worktrees it has (`home_doc` in `main.rs`, `Project::worktrees` in `live.rs`). A worktree's folder does not come back, so this is the one case where an entry is forgotten without the user: at the backend's start and on each listing, `repos::prune_worktrees` removes a worktree whose folder is gone, with its index files. `repos::mark_worktrees`, at the start, marks the entries an older backend registered. A wiki synced in a worktree is the repository's wiki and is merged back, so it must not differ by where it was written: the repository's name in its notes is that of the main checkout (`cw_wiki::git::repo_name`), not the worktree's folder, and the `.git` file a worktree has in place of the folder is no file of the repository (`walk` in `crates/cw-parse/src/scan.rs`).
- **Generation.** `cw_wiki::service` holds the operations that the CLI, the server and the MCP tools share. `service::update` rescans the repository into the index, then `generate::generate` scans, plans, freezes names, renders, lints and writes. `cw_vault::lifecycle` decides for each note whether it is written, proposed or left alone. Bump `TEMPLATE_VERSION` in `crates/cw-wiki/src/generate.rs` when a rendering change should refresh every note.
  - **File-level mapping** (`crates/cw-wiki/src/filemap.rs`, called from `plan::plan`). A source file whose language has no parser, named by `Language::file_level_name(path)` from its extension (`.m` is Objective-C; data and prose are never source), gets no symbols and no units from `units::discover`. `filemap::build` groups such files instead: a file at `<container>/<project>/…` (`src`, `tests`, `apps`, `packages`, …; `CONTAINERS`) belongs to the unit `<container>/<project>`, every other file to the root unit, and a unit of fewer than 3 files folds into the root. Beside parsed code the root unit also needs 3 files, so a few scripts next to a Rust workspace get no notes. Each unit has a note `unit:<key>` under `01-Core/<slug>`. A folder gets a note `dir:<repo-relative path>` when it holds at least 3 files, counting those of the folders below it that have none (they roll up); at most 300 get one, the largest in lines first, and a pinned (explained) note is never cut while its folder has a file. Both are `NoteKind::Concept` notes with the agent's sections (What it does, How it works, Gotchas), and their `sources` are the largest files of the folder, 10 at most. Rules write only facts that cannot be wrong: the files with language and size in lines, the totals, the sub-folders with notes, the place under the unit. No symbols, imports, call links, dependencies or git numbers (those would rewrite the note at every commit). They are planned after every other content note, so no name another note reserved changes, and a repository with no such files plans exactly what it did before. The home note says "is a Swift codebase of N folders and M source files, mapped at file level: CodeWiki has no parser for Swift yet" (or, beside parsed code, adds "M source files in X are mapped at file level"); "no code in a language CodeWiki maps" stays for a repository with no source file at all. A language that gets a parser leaves the fallback by getting a `Language` variant with `has_symbol_support`. Health, dead code, security and contracts stay gated on `has_symbol_support`.
- **CodeWiki calls no language model.** There is no provider, no prompt and no key for writing notes. Do not add one: a coding agent with the plugin writes what rules cannot, it reads any file it needs, and it is already signed in.
- **Who writes a note.** Each `## ` section of a note belongs to rules or to a coding agent, by the note's kind: `NoteKind::agent_sections` in `crates/cw-vault/src/note.rs`. Rules own every fact (summary, Source, Items, Depends on, Used by, See also, an integration's Used for and Configuration, a pattern's When to apply and The pattern). The agent owns the rest (What it does, How it works, Gotchas, Wire-up, Auth mode, Why, Don't). A flow's diagram and an operations note's commands are facts inside a section whose prose is the agent's (`NoteKind::fact_fences`): the rule's blocks first, the agent's prose after.
  - **One weave, two directions.** `cw_vault::explanation::weave(base, agent_sections, kind)` puts an agent's sections into a note and leaves the rest of `base` as it is. When an agent submits, `base` is the note on disk. When the code changes, `base` is the fresh draft and the agent's sections come from the old note (`extract`). `note::split` and `note::join` are the one definition of a note's layout; `render.rs` builds its notes with `join`.
  - **The record.** `NoteEntry::explained` holds the headings the agent wrote, the files it wrote them from with their hashes, and the commit; `model` names the agent; `behind` holds why the explanation may be out of date. A submission does not make a note "edited by a person": it updates `body_hash`.
  - **At a sync** (`generate.rs`): the draft changed and nobody edited the note, so `Action::Merge` writes the weave. Only a file of `explained.sources` changed: the note stays and is marked `behind`. A person edited it: a proposal, whose text keeps the agent's sections. The file is gone: rules write the note again and `explained` is cleared. A link of the agent's that leads to no note, because the run removes that note or an earlier one did, becomes plain words, also in a note whose facts did not change, and the note is marked `behind` for it.
  - **An explained note keeps its place.** Which modules, types, integrations and patterns get a note is a ranking with limits (`plan.rs`). `plan` takes the ids of the explained notes and never cuts one whose subject still exists: an explanation is lost only with its subject, never to a neighbour that got more references.
  - **The way in** is `crates/cw-wiki/src/explanations.rs`: `queue` (notes behind first, then never explained), `brief` (one note, the agent's sections, the files to read, the limits) and `submit`. A submission holds sections and pictures, never a whole note, so an agent cannot change a fact. `submit` checks everything, then answers `Saved`, `Issues` (every fault at once, nothing written), `Changed`, `SyncFirst` or `Proposed`. The routes are `GET /v1/repos/{id}/explanations` and `GET`/`PUT /v1/repos/{id}/explanation`; the `PUT` answers 200 for every outcome, because a client keeps only one line of an error. The MCP tools are `list_waiting_notes`, `get_note_brief` and `submit_note`. **Claims** (`crates/cw-server/src/claims.rs`, in memory only): `GET /v1/repos/{id}/explanations?agent=<id>` (1 to 64 characters) leaves out the notes other agents hold and lends the notes it lists to that agent for 30 minutes (`cw_core::CLAIM_MINUTES`); `all=true` lists every waiting note, with the claimed rows marked, and cannot go with `agent`. The `PUT` takes the same `agent`: a note it saves or proposes is freed, and the agent's other claims are renewed. `list_waiting_notes` has `claim`. The bridge gives every listing with `claim: true` an agent id of its own (`<pid>-<start nanos>-<count>`, `ClaimIds` in `crates/codewiki-mcp/src/main.rs`), because the main agent, its note-writer and one launched after `/clear` share one bridge; it remembers which id each listed note went to and `submit_note` sends that id, or the bridge's own `agent_id` for a note not claimed through it. A listing with `claim: true` therefore does not hand back the notes an earlier listing of the same session holds.
  - **Notes of code that is gone** (`crates/cw-wiki/src/gone.rs`, called from `generate.rs`). A note nobody wrote in goes with its subject at once. A note with written work, an agent's explanation or its owner's edits, is judged first:
    - **It moved.** `carry_moves` gives the old entry the id and the path of the planned note of the same kind and name, when git saw the file move there or when exactly one old and one new note match. The files are renamed after the drafts passed the linter, the weave keeps what was written, and `behind` says `its subject moved from`. Any other case is listed in `Report::possible_moves` and nothing is carried.
    - **Its unit changed.** A note keeps its path while its id stays, so a unit that changes its folder (a `package.json` that gets a `name`, Python folders that become one project) would leave its notes in a folder whose map the run removes, and the next run fails on `[[_index]]`. `follow_units` moves each such note, whatever is written in it, to the folder it is planned in, keeping its file name and its picture; one that holds written work is listed in `Report::moved` like a note whose subject moved. A note moves only into a free place, and only out of a folder under `01-Core` that no planned note uses any more.
    - **It is gone.** The note is deleted only when no source of it has an uncommitted change (`git::changed`) and git holds the note and its pictures as they are (`git::recoverable`). Otherwise it stays with `NoteEntry::gone` set (`Gone::Uncommitted`, `Gone::Unsaved`), its state is `NoteState::Gone`, and the next sync judges it again. Without git nothing with written work is ever deleted.
    - **A note its owner wrote** (`Origin::Adopted`) is about the repository paths it names in code spans, anywhere in its text (`gone::cited`, kept in `NoteEntry::cited`). A path counts only if it exists or a commit once held it. A file git saw move is followed: the path is rewritten in the note, where git holds the note. A note that names only paths that are gone is never deleted by a sync: it gets `Gone::Pending` and all such notes wait in one proposal of kind `retire` (`proposal::create_retire`). Approving deletes them, leaving out the paths in the body's `keep` (`explanations::approve_keeping`, `POST …/proposals/{pid}/approve`); a note left out, and every note of a rejected one, gets `Gone::History` and is never proposed again. A note that names some paths that exist stays (`Report::partly_gone`), and one that names no path is never judged.
    - **After a removal** (`gone::after_removal`, at a sync and at an approval): a link to a note that just left becomes plain words in the notes that stay, in an explained note's agent sections always, in a note its owner wrote or edited only where git holds it; no other dangling link is touched. An attachment only removed notes showed is deleted, folders left empty are removed, and a pending proposal for a note whose subject went is superseded.
    - **What counts as a note.** A note with `gone` set is in the vault and not of the wiki: `VaultMeta::live_notes` is the count the briefing, the status and the report give, the waiting list leaves it out, and the search index leaves out the ones that wait to be retired. `health::doc_drift` reports it once, as `SubjectGone`. `Report::summary` holds the sentences the command line, `sync_wiki` and the app's Sync page all show.
  - **A note a person edited is never written**, by a sync or by an agent. An agent's text for it is a proposal of kind `agent`, with its pictures; a sync's is of kind `sync`, and neither replaces a pending one of the other. `explanations::approve` and `reject` treat each by its rules. After an agent's proposal is approved the note stays its owner's: `body_hash` keeps the old value.
  - **Pictures** are a coding agent's, never the rules': a picture explains what a thing is for, which rules cannot know. The library (`cw_illustrate::library`) has four components, `Picture`, `Flow`, `Step` and `Callout`, and `review` holds a picture to its limits. A note's pictures are in `<Note>.openui` beside it, each under a `# section: <heading>` line (`parse_pictures`, `serialize_pictures`); the Markdown stays clean. A sync deletes the picture file of a note no agent explained. The app draws each picture under the heading of its section (`markdown::prepare_note_with`, `illustration.rs`). When you add a component: the library, `review`, the renderer's `match`, `plugins/claude-code/skills/write-notes/pictures.md`; tests pin the last three to the first.
  - **The agent view.** `query::agent_view` is what `read_note` gives an agent and what "Agent view" shows in the app: no pictures, and no `How it works` while rules wrote it. A section the agent wrote stays in.
  - **The skill** is `plugins/claude-code/skills/write-notes/SKILL.md`, which Claude Code also offers as `/codewiki:write-notes`. `crates/codewiki/tests/plugins.rs` pins every tool, argument, answer, section and number it names to the code. Codex has its own copy, `plugins/codex/skills/write-notes/SKILL.md`. The session-start line about waiting notes (`briefing.rs`) states a count and is an order only when auto explaining is on (`explain_for`): the switch is on, `source` is `startup`, `resume` or `clear`, and neither the session's folder nor the vault root found above it is a linked git worktree (`cw_wiki::git::is_linked_worktree`). The hook leaves the order out when the host reports plan mode (`permission_mode`, which Claude Code's SessionStart input may not carry); the order itself tells the agent to skip it in plan mode. With the switch off the hook does not read stdin. The order carries the user's count (`Explain::ClaudeCode(Count)`, `Explain::Codex(Count)`). Then, for Claude Code, the first message launches the agent `plugins/claude-code/agents/note-writer.md` (`codewiki:note-writer`: Sonnet, background, up to 20 notes, `list_waiting_notes` with `claim: true`, listed once); a count above `MAX_LIMIT` launches one agent per 20 notes, all at once, the last with the rest (`launch_order`; the count is capped at the notes that wait). For Codex, the `write-notes` skill runs after the first request and lists 20 at a time until the count is reached (`codewiki hook session-start --agent codex`, which the Codex `hooks.json` and `config.toml` sample pass). In every other case the line is a fact and says to write notes when asked or for files changed. A folder kept from coding agents gets no briefing at all, as before. `plugins.rs` pins the skills, the agent and the order's wording. Limit: a `codewiki update` run outside the backend (on the command line) or an edit in Obsidian does not move N until the next `notes_rev` bump or until the repository is opened again.
- **Folders kept from coding agents.** `cw_core::agents_off` reads `agents-off.json` in the data directory (`{"version": 1, "folders": [...]}`): an entry covers its folder and everything below it, and a folder that holds an entry is blocked too, because indexing it would index the entry's code (`agents_off::blocking`: `Block::Covered` first, then `Block::Contains`; folders are compared by whole names, so `D:\work\client` neither holds nor lies in `D:\work\clients\x`). A list that cannot be read, or that has an empty or relative entry, fails closed. The texts people and agents read are functions of the module (`refusal`, `repo_refusal`, `unreadable`); the bridge, the command line and the app call them, and the exact-text tests pin them there. Three things obey the list. `codewiki hook session-start` prints nothing when the project folder or its vault root is covered or holds an entry. The MCP bridge (`screen` in `crates/codewiki-mcp/src/main.rs`, `guard.rs`) refuses every tool when a session folder (the current folder or `CLAUDE_PROJECT_DIR`) is covered or holds an entry, with `refusal`, which names the entry. A `repo` argument (path, id or name) that is or reaches such a folder gets `repo_refusal`, which names no path and stops that repository alone. `screen` costs at most one `GET /v1/repos`; `Bridge::call` then checks the repository the call reaches by the id it resolved, through one listing, so a lookup that failed in `screen` or `repo_id`'s fallback to a name cannot reach a kept repository. A refusal found there travels as an error marked `REFUSED`, and `answered` in `call_tool` turns it into a normal text result. `list_repos`, `get_workspace` and `get_contracts {workspace: true}` leave out covered and holding repositories, and refuse when the list cannot be read. The bridge's tests serve canned JSON from a stand-in backend named by `CODEWIKI_URL`. The plugin skills tell the agent to stop at either refusal; `plugins.rs` pins their lines to the two texts. `codewiki agents off|on|list|status` and the app (Settings → Repositories, Home rows, palette) write the list; the app does so through `cw-core`, not the backend. Home shows four states of a project (`live::Kept`: open, its own entry, under a parent entry, holding an entry), worked out in `refresh_agents_off`. With a remote backend the bridge reads the backend's repository paths as local paths: one that names a kept folder here, or holds one, is refused and hidden (on Windows a Linux path reads as a path on the current drive), and the others are not hidden. A `repo` given as a path is always read as a local path, so an agent cannot register a remote backend's new repository by its path there. Limit: a visible route called only by a hidden repository leaves the matched list in `get_contracts` and does not show as unconsumed (`guard::hide_in_contracts`).
- **Settings.** The embedder, its model and the keys and addresses each have an environment variable and a place in `settings.json`: `CODEWIKI_EMBED`, `CODEWIKI_EMBED_MODEL`, `CODEWIKI_LMSTUDIO_URL`, `CODEWIKI_LMSTUDIO_KEY`, `CODEWIKI_LLAMACPP_URL`, `CODEWIKI_LLAMACPP_KEY`, `CODEWIKI_LEMONADE_URL`, `CODEWIKI_LEMONADE_KEY`, `CODEWIKI_MISTRALRS_URL`, `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `OLLAMA_HOST`. `cw_core::settings::Resolved` gives the value in effect and where it comes from: the variable when it is set, then the file, then the default. A setting is named by its variable, and the table of them is `settings::ALL`.
  - **Who reads them.** `cw_wiki::semantic::configure` puts the embedder in a slot that can change while the program runs; the server calls it at its start and after a change, the CLI at its start, so a change needs no restart. `from_env` in `cw-embed` reads the environment alone.
  - **Retired settings.** The sections `llm`, `anthropic` and `cliproxy` held the settings of the writer CodeWiki once called itself, two of them an encrypted key. `settings.json` keeps sections it does not know, so these are removed by name: `settings::RETIRED_SECTIONS`, at the start of `serve` (`drop_retired`) and on every `update`. A retired variable that is still set gets a line in the log; `CODEWIKI_EMBED_DEVICE` is one of them.
  - **Routes.** `GET /v1/settings` describes every setting; `PUT /v1/settings` changes the fields it names (`null` clears one); `POST /v1/settings/test/embed` sends the chosen embedder one small request (`probe`) and answers 200 with `ok` true or false. The work is in `crates/cw-server/src/settings.rs`. A field whose variable is set is refused. A server that listens beyond this machine refuses every change (`ServerConfig::settings_writable`): someone holding its token could point a provider's address at their own host and be sent the API key.
  - **Secrets.** An API key, and the token in `remote.json`, are encrypted for the current Windows user by `cw_core::secret` (the Data Protection API), one of the two modules of the workspace with `unsafe` code (see "The tray"). No route returns one: a key is reported as unset, saved, given by the environment or unreadable, with the last four characters of a saved one. Another system cannot save a secret and takes it from the environment.
  - **Stale vectors.** A changed embedder leaves the old vectors in the index until the next update. The index records which embedder made the vectors of each kind of document (meta key `vectors_embedder:<kind>`), and a search compares only those the current embedder made; until the update it is full-text alone. While a run replaces another embedder's vectors the key holds a marker that is no embedder's name, so a run cut short never counts as current; `vectors_waiting:<kind>` says whether documents still wait, and `semantic::behind` reads both.
  - **The model field.** `embed.model` is a model name of the chosen server. Model names do not carry across servers, so `settings::change` clears it on any change of provider that names no model, unless the environment sets it. A server provider with no model cannot be built: `embed.problem` says to choose a model, and search is full-text alone until one is named.
  - **Tests never read the machine's settings.** The server reads its environment through `ServerConfig::env`, which the route tests replace, and the embedder slot holds what the environment alone names until `configure` is called. Keep both, or a test calls the provider configured on the machine that runs it.
- **Embedding servers.** CodeWiki runs no embedding model itself and never downloads one: the user runs a server, and CodeWiki asks it for vectors. Do not bring a model engine back, under any name.
  - **Providers.** `local` (word forms, in process), `lmstudio`, `ollama`, `llamacpp` (Llama for Windows and `llama-server`), `lemonade`, `mistralrs`, `openai` and `none`, in that order on the page (`cw_embed::PROVIDERS`). Defaults: LM Studio `http://127.0.0.1:1234`, Llama `http://127.0.0.1:9931`, Lemonade `http://127.0.0.1:13305`, mistral.rs `http://127.0.0.1:1234`, Ollama `OLLAMA_HOST`. LM Studio, Llama and Lemonade have an optional key (`CODEWIKI_LMSTUDIO_KEY`, `CODEWIKI_LLAMACPP_KEY`, `CODEWIKI_LEMONADE_KEY`); mistral.rs has none; `openai` needs `OPENAI_API_KEY`. A server provider needs a model. Spike S5 in `spikes/VERDICTS.md` records what the built-in engine measured, before it was removed.
  - **One client.** `OpenAiEmbedder` in `crates/cw-embed/src/lib.rs` serves every OpenAI-style provider, given a `Server`: its address, key, extra body fields and the name used in errors and in the vector name (`<provider>:<model>`). Texts go in batches of 64, each cut at 8,000 characters. Its quirks sit in one place:
    - an address pasted with `/v1` works like the bare one;
    - a 401 or 403 names the key setting to fill in;
    - a batch refused as too long (HTTP 400, 413, 422 or 500 with a message about length) is sent once more with each text cut to 2,000 characters; refused again, its texts go one at a time (`one_by_one`), and a text refused alone once more cut to 400 characters (`TINY_CHARS`), its prefix kept; a text still refused is an error;
    - mistral.rs is sent `truncate_sequence: true`, or a long text is an error;
    - llama.cpp and mistral.rs embed with the model they hold, whatever `model` names: until an embedder instance's first call succeeds, it reads the server's `/v1/models` (`check_listed`) and fails with "<server> does not list <model>; choose a model it serves" when the model is not there. The Settings page warns the same way for any server whose list lacks the chosen model;
    - a request waits 120 s (`REQUEST_TIMEOUT`); the first call of an embedder instance waits 300 s, so that a server can load a model.

    An embedder error never quotes a text it was given.
  - **Model lists.** `GET /v1/settings/embed/models` lists what the provider in effect offers at its address in effect: `{ provider, reachable, models: [{ id, embedding, loaded }], problem }`, embedding models first, 10 s at most. The parsing for each server is beside its provider in `cw-embed`. Settings → Semantic search fills its Model select from it, and falls back to a text field when the server does not answer. While the server does not answer, that page asks again by itself (`settings_view.rs`, the rules in `connection.rs`): after 3 s, then 6, 12, 24 and 30 s at the most (`EMBED_FIRST`, `EMBED_CAP`), only while the page is open, the backend is local and the window is on screen (a minimized window idles, a hidden one stops, and showing the window resumes). "Refresh" asks at once and keeps the shown list until the answer comes. When the server comes up, the toast "Connected to <server>" shows.
  - **Prompt prefixes.** `crates/cw-embed/src/prefix.rs` holds the text some models expect before a query and before a document: `gemma`, `qwen3`, `nomic`, `mxbai`, `bge` and `e5`, matched by the model's name, the first rule winning. A rule adds `+<id>` to the vector name, so vectors made with and without a prefix are never compared. It applies to every HTTP embedder. Each prefix is the one on the model's card; a test pins a model name for each rule.
  - **The job.** `crates/cw-server/src/embed_job.rs` finishes embedding after a Sync, for every embedder on every platform. It embeds with no lock held and takes `write_lock` for each batch's write alone; one job runs at a time, in the background, nothing of it on disk; a run that an update overtakes starts over (`Inner::updates`). The routes are `GET /v1/embed/job`, `POST /v1/embed/reembed` and `POST /v1/embed/cancel`; a backend that listens beyond its machine refuses all three. `/v1/status` reports the job as `model_job`, a name kept from before. A failed batch ends the job with its error (shown on the Settings page, kept in the log); the repository stays behind, nothing retries, and the next Sync, Test or reembed tries again. The job has no retry loop; only the Settings page asks again for the model list (see "Model lists"). A backend that starts with a repository behind tries once.
  - **Updates stay quick.** An update of a wiki embeds for a second in each of its steps and leaves the rest to the job (`semantic::set_inline_budget`).
  - **From the built-in model.** `cw_core::settings::retire_builtin` runs at the start of `serve`, beside `drop_retired`: a saved `embed.provider` of `builtin` becomes `local`, `embed.model` is cleared, `embed.device` leaves the file, and under `<data dir>\models\` the folders the old store wrote (`.partial` and each folder that holds a `manifest.json`) are deleted, then `models` itself when it is empty; other files stay, and the log says how much was freed. `CODEWIKI_EMBED=builtin` in the environment cannot be rewritten: `embed.problem` says the built-in embedder was removed, and search is full-text alone. `cw_update::recover_and_clean` removes an old `cuda\` folder from an installation, and `uninstall.ps1` does too.
  - **Tests.** No test calls a model server. The background job takes its embedder from `ServerConfig::host` (`Host`), which `embed_job.rs` replaces with stand-ins; the route tests in `api.rs` keep `Host::default`, the process's embedder slot. Every test harness that builds a router or calls `serve`, and every test of `cw-wiki` that builds an index, first configures that slot from empty settings and no environment (`no_model_server` in `crates/cw-server/tests/api.rs`, `embed_job.rs` and `crates/cw-wiki/tests/support/`), so the slot never builds from the machine's environment. A test that chooses a server points its address at a stand-in or a closed port (`closed_port` in `api.rs`), never at a default port. `crates/cw-server/tests/embed_job.rs` is a test program of its own because it switches the process's embedder. `crates/cw-embed/tests/wire.rs` drives each provider against a stand-in server whose shapes come from the servers' own docs and source, which the file's header cites.
- **Tests.** Unit tests sit beside the code. `crates/cw-wiki/tests/` has one file per analysis plus `pipeline.rs`; the server's routes are tested in `crates/cw-server/tests/api.rs`. `explanations.rs` there covers what an agent may write. `wire.rs` in `cw-embed` drives each HTTP embedder against a stand-in server, so no API key is needed.
- **Orientation.** `obsidian/00-Architecture/` holds the generated crate dependency flow and the startup flows of `codewiki` and `codewiki-app`.

## Adding a feature

A backend feature usually touches four places: the logic in `crates/cw-wiki/src/`, a route in `crates/cw-server/src/api.rs`, a subcommand in `crates/codewiki/src/main.rs`, and a tool in `crates/codewiki-mcp/src/main.rs`. An app page is a page function that builds a `Doc` in `crates/codewiki-app/src/pages.rs` or `live.rs` (see App look), plus a palette entry in `palette.rs`. A new setting is a block in the function of its category in `settings_pages.rs`, a field in `Model` when it needs new data, and an `Action` that `run_action` or `run_settings_action` carries out.

## Adding a language

C# followed Java, Go followed C#, and Kotlin followed Java; each language after them follows the same places. A language is mapped when its `Language` variant has `has_symbol_support`, and it then leaves the file-level fallback by itself (remove its extensions from `Language::file_level_name`; an extension that stays there, such as `.axaml`, stays file-level).

1. **Grammar.** A `tree-sitter-*` crate in `crates/cw-parse/Cargo.toml`. Read its `node-types.json` in the cargo registry before writing the walk, cite it in the file header (`java.rs`, `csharp.rs`), and never guess a node or field name: test each construct. Parse a sample of every construct and read the tree before writing the walk: a grammar may lose the rest of a file on one construct (`tree-sitter-kotlin-ng` does on `fun interface I { ... }`, which `kotlin.rs` blanks out of a copy of the source, byte for byte, so every position still stands) and may give a form no field (a Kotlin `Foo<Int>(1)` is two comparisons), which the walk then has to recognise by shape.
2. **Core.** `crates/cw-core/src/model.rs`: the `Language` variant, `from_path`, `as_str`, `parse`, `has_symbol_support`, and the doc comments of `SymbolKind` (how the language's kinds map).
3. **Parser.** `crates/cw-parse/src/<language>.rs`, a hand-written walk with no query files, modelled on `java.rs`: one module per package or namespace shared by many files, the module symbol emitted by the parser, `import` facts, types, functions, calls, inheritance edges, attributes into `attrs`, doc comments. Export it in `lib.rs` and add its arm in `scan.rs` (symbols that two files declare are kept once; `merge_partial` is C#'s partial types, `merge_package` Go's package). A parser sees one file and cannot read a build file: when the name of a module depends on one (a Go package is the module path of its `go.mod` plus its folder), `scan_repo` reads the build files first and gives the parser the module name and what else it needs, such as the names packages call themselves (`go.rs` takes a closure, as `parse_typescript` does). Declarations whose names two files share are no error: `init` and `_test.go` files of one package repeat names, and the first stays.
4. **Imports and names.** `crates/cw-parse/src/lang.rs`: the platform roots, a default module for a file with no package, `link_<language>` and its arm in `link_imports`. `link_imports` also gets what the build files say (`GoBuild`: the `go.mod` files and what they require), which an import path needs to be told from a package of the repository, the platform and an outside package. `resolve.rs`: scopes the language sees without an import (C#'s enclosing namespaces), the common method names of its library that must not bind to a repository type (`COMMON_CSHARP_METHODS`, `COMMON_GO_METHODS`), and whether an import is a re-export: `resolve_abs` follows a name through the `use` lines of the modules on its path, which is Rust's rule and nobody else's, so the modules of a language whose imports bind a name in one file (C#, Go) are listed in a set it skips; without that, glob imports made name resolution exponential. A language whose types are no scope for the names in their methods (Go) is listed in `lookup_from`.
5. **Units** (`crates/cw-wiki/src/units.rs`): a `Family`, how a unit is found from build files, its name, dependencies between units, `is_test_file` and what else makes a file test code (`Units::is_test`), and the entry points. A language whose sources sit in folders named by their build files gets a unit per build file (a `.csproj`, a `go.mod`); `Unit::lock` keeps the lock file (`packages.lock.json`, `go.sum`) apart from the files a note describes. What a unit is called, what its dependencies are and whether `declared` holds for a lone entry point are each a line in `discover`.
6. **Planning and rendering** (`plan.rs`, `render.rs`): `Repo::is_test`, the operations sources, `language_name`, `unit_noun`, `build_role`, `unit_commands`, `entry_label`, the pattern stub and its code fence.
7. **Packages** (`manifests.rs`): the reader of the build files for the version asked for and the version locked, and `Machine::describe` for what a package is. Tests never depend on what the machine holds.
8. **Smaller places.** `explain.rs` (`return_type`, the method separator), `doctext.rs` (the fence language of an untagged block), `health.rs` (`is_test_symbol`, entry points that are not dead, what is a package's API and so never dead, `parameter_count`).
9. **Impacted tests** (`crates/cw-wiki/src/testmap.rs`): one more `TestLanguage` in `LANGUAGES`: which files are test code, which of their parts are tests, and the command that runs them. Reachability, the report, the MCP tool, the CLI and the app need no change. Where a test reaches its code without importing it (a Go test file builds with every file of its package), `add_go_package_dependents` adds those dependents to the reachability map when the map is built; they are not edges of the index, which a package of hundreds of files would fill with tens of thousands. A command that runs many files at once overrides `TestLanguage::commands` to fold them.
10. **Tests.** Parser tests in the parser file, a repository scan test in `scan.rs` (symbols by kind, edges with their `Confidence`, outside packages), unit and manifest tests, an end-to-end test in `crates/cw-wiki/tests/pipeline.rs` (`a_csharp_solution_gets_a_full_vault`, `a_go_module_gets_a_full_vault`), and one in `crates/cw-wiki/tests/testmap.rs`. A test that needs a language with no parser uses one that still has none: Swift or Ruby (`pipeline.rs`, `filemap.rs`, `model.rs`); a language leaves that list when it is mapped, and the next one's tests switch. `TEMPLATE_VERSION` stays as it is: no note of another language may change. Finish with a live check on code that is already on the machine (a module cache has Go; read-only, copy it): the time of the scan, the notes, a run that writes nothing the second time.

Security findings and API contracts stay Rust-only. Impacted tests cover every mapped language.

**What the C and C++ slice taught about this list.** Step 3's "one module per package or namespace" does not fit a language with no packages: a module is whatever the other files make it, and C and C++ needed a pass over every file before any is parsed (`CPlan::build` in `cfamily.rs`: the language of each `.h`, the module of each file, the directories an include may name) and a pass after (`cfamily::merge`: a declaration and its definition become one symbol, a method defined out of line joins its class). Step 3's "keep the first" is wrong for them, since the first file in path order is the source and the symbol stands at the header; the scan defers C and C++ symbols to `merge`. Step 5's units come from a build file that is a program, not data: `cmake.rs` follows variables, `add_subdirectory` and `if` branches, and `units::discover` reads it again for itself (`RepoFacts` is rebuilt from the index, so it cannot carry the result). A language whose build file can hold test targets needs `Units::tests` filled before the "a unit needs a non-test symbol" filter drops them. A parser that leaves symbols with no file of their own (the header's symbols stand at the header) still needs every source file to belong to a unit: `units.rs` asks `c_module_map` for the module of each file instead of looking for a symbol in it. Step 7: a library the repository names is matched to the first segment of the include (`cdeps::names_library`), and nothing is guessed.

**A language that shares its packages with another** (Kotlin with Java) names the same module in both: the module symbol is kept once whichever file came first, so look at every parsed file, not at `facts.symbols`, when a set of modules must be told by language (`kotlin_modules` in `resolve.rs`); `link_imports` hands both languages the union of their packages; a bare method name on a receiver of unknown type never matches across the two (it would bind the platform's `readLine` to a repository method), though paths and imports do; `Family` in `units.rs` is one family, and `TestLanguage::covers` in `testmap.rs` lets one entry serve both.

**Go** (`crates/cw-parse/src/go.rs`, `gomod.rs`): a package is a module named by its import path, `example_com::app::internal::store` for `example.com/app/internal/store`, so an import finds it without a lookup; an external test package (`package store_test`) is the module `<package>_test`. A method belongs to its receiver's type, pointer or value; exported names are `Public`, the rest `Crate`. Embedding (of a struct in a struct, an interface in an interface) and `var _ Iface = (*T)(nil)` are the "implements" edges; a type that satisfies an interface only by its methods has none. A unit is a `go.mod`, named from its module path without `/vN`, holding its `cmd` folders; dependencies come from `require` and `replace` lines that name another module of the repository, else from imports. `vendor/` is left out when it holds `modules.txt`, `testdata` is test code, and a file with `// Code generated ... DO NOT EDIT.` before its `package` is parsed (its symbols exist and are called) and carries the attribute `generated`, which keeps it out of notes and dead-code findings. Impacted tests are `go test <package> -run '^(TestA|TestB)$'` with `-C <module folder>` for a module below the root, and `-bench` for benchmarks; past 8 names a package runs whole.

**Kotlin** (`crates/cw-parse/src/kotlin.rs`, `gradle.rs`; the unit, test and version parts are Java's, in `units.rs`, `testmap.rs` and `manifests.rs`): Kotlin and Java files of one `package` are one module, so a Java class and a Kotlin class of `com.acme.store` are siblings; the folder says nothing, the declaration wins, and a file with none is in its folder's default package as for Java. Classes (data, sealed, inner), `object` and `enum class` are classes and an enum, entries are constants, interfaces (`fun interface`, annotation classes) are interfaces, `typealias` is a type alias. A companion object is no symbol: its members belong to the class around it. Top-level functions are `Function`s of the package and top-level properties are symbols (`val` and `const val` a `Const`, `var` a `Static`, as for an `object`'s); a property of a class, a constructor's `val` included, is no symbol, as a Java field is none. An extension function belongs to the place it is written in, never to its receiver; its attribute `extension` lets `x.shout()` on a receiver of unknown type find it. `internal` and `protected` are `Crate`. A call whose name is a type (`Foo(1)`) is a construction: a reference to `Foo` and a call of `Foo::Foo`. Default imports are not imports, so `listOf` or `println` is a bare name that only a function of the same package or an import answers; `COMMON_KOTLIN_METHODS` keeps stdlib extensions off repository methods. `kotlin.*` and `java.*` are the platform, `kotlinx.*` a library, found in a build file by its artifact (`kotlinx-coroutines-core` is `kotlinx.coroutines`). A Gradle or Maven module with both languages is one unit, named for both (`Kotlin and Java module`) and for the larger one in the home note. Test files are `src/test`, the source sets named `<x>Test` (`commonTest`, `jvmTest`) and, for Kotlin, the stems `Test`, `Tests`, `IT` and `Spec`; `.gradle.kts` files are build files, not source, and other `.kts` scripts are parsed as Kotlin. A top-level `fun main` and an `@JvmStatic fun main` are entry points. The version catalog `gradle/libs.versions.toml` is read for a module with Kotlin files (`libs.<alias>` in its build file; only the catalog named `libs`), and kept in `Unit::lock`. Impacted tests, for Java and Kotlin together (`JvmTests`): a test is a method with `@Test`, `@ParameterizedTest`, `@RepeatedTest`, `@TestFactory` or `@TestTemplate`, or a class extending a Kotest spec style (attribute `kotest`); the command is `./gradlew :<project path>:test --tests "<pkg.Class>"` (once for each class, `Class*` when a nested class holds tests; `gradle` without a wrapper; `-p <root>` when `settings.gradle(.kts)` is below the repository root; the task of a source set `<x>Test` is `<x>Test`, and `commonTest` runs `allTests`, which takes no filter) or `mvn [-f <pom>] [-pl <module>] test -Dtest=<Class>,<Class>` (`-pl` below an aggregator `pom.xml`), one run for each module and task, the whole module past 8 classes. Not followed: a Java call to a top-level Kotlin function through `UtilsKt`, a Gradle `projectDir` set in `settings.gradle`, Android's own test tasks.

**C and C++** (`crates/cw-parse/src/c.rs`, `cfamily.rs`, `cmake.rs`, `cdeps.rs`): one walker for both, because the C++ grammar is the C one plus more node kinds; the grammar is chosen per file. `.c` is C; `.cc`, `.cpp`, `.cxx`, `.c++`, `.hpp`, `.hh`, `.hxx`, `.ipp`, `.tpp` and `.inl` are C++; a `.h` is C++ when it uses what only C++ has (`class`, `namespace`, `template`, an `#include` of a header with no extension), outside the `#ifdef __cplusplus` blocks C headers keep for C++ callers, else when the source of its name is C++, or its folder has C++ sources and no C, else C. A **module** is a header and the source of its name (`src/net/socket.h` and `.c`, or a header and a source of one name in two folders when each is the only one), named from the header's path without `src`, `lib` and `include` (`net::socket`); a namespace is no module, it is the attribute `namespace:a::b` of the symbols in it, so names are matched against it and never qualified by it. A declaration and its definition are one symbol at the header, with `impl:<file>` for each source that defines it; `void Foo::bar() {}` is a method of `Foo` wherever `Foo` is declared; a function that a header declares and another module defines is merged when that module includes the header. Symbols: functions, methods (constructors and destructors included), `struct`, `union`, `enum` and enumerators, `class`, `typedef` and `using` (a typedef'd struct whose tag differs only in spelling is the typedef's name), variables and constants (`const` and `constexpr`), object-like macros with a value (a constant) and function-like macros (`Macro`); include guards and empty flags are none; forward declarations of types are none; a template is one symbol with the attribute `template`, and a specialization none. A class of pure virtual members and no data is an `Interface`, one with some pure virtual members is a `Class` with the attribute `abstract`. `static` and an anonymous namespace are `Private`, `protected` is `Crate`; what only a source defines and no header declares is `Crate`. Every branch of `#if` is parsed and the scan keeps the first symbol of a name. A macro that stands alone on a line (`FT_BEGIN_HEADER`) or wraps a return type (`FT_EXPORT( int )`) is set aside in a copy of the source, byte for byte, because the grammar otherwise reads the declaration after it wrongly. `#include "x.h"` is an import of a repository file (relative to the includer, then the CMake include directories, then `include/`, `src/` and the like, then the only header of that name); an include is a glob import of the header's module, and the resolver (`lookup_c` in `resolve.rs`) sees the module itself and what it includes, transitively, nearest first, and binds nothing when two headers at one distance both declare the name. An include that names no repository file names a library only when `find_package`, `FetchContent_Declare`, `vcpkg.json` or a Conan file declares one that matches its first path segment (`<boost/asio.hpp>` is `Boost`); the platform's headers and anything else name nothing. A call is a function, a method, `Namespace::f()`, a constructor (`Foo(1)`, `new Foo`, `Foo x(1)` are calls of `Foo::Foo`), a function-like macro, or `obj.m()` on a receiver of unknown type, which binds by its name only when exactly one visible method has it and the name is not a common one of the standard library. **Vendored trees** (`third_party`, `vendor`, `external`, `extern`, `deps`, `_deps`, `3rdparty`) are not parsed when the repository has C or C++ outside them, and an include into one names the library by its folder. A **unit** is a CMake target (`add_library`, `add_executable`) with the files it lists, through variables, `file(GLOB)` with a literal pattern, `target_sources` and `add_subdirectory`; a header or a source it does not list falls to the target of its folder; without CMake a unit is the first folder of the module (`libs/zip` below a container folder), the root otherwise. `target_link_libraries` between two targets of the repository is a dependency. Entry points are `main`, `wmain`, `WinMain` and `wWinMain` in a source file. A target is a unit of tests when `gtest_discover_tests` and the like register it, or it links GoogleTest, Catch2, doctest or Boost.Test, or all its files are test files; `*_test.c(c|pp)`, `test_*`, `*_tests.*`, `*Test.cpp` and the `test` and `tests` folders are test files. Tests are `TEST`, `TEST_F`, `TEST_P`, `TYPED_TEST`, `TEST_CASE`, `SCENARIO`, `TEST_CASE_METHOD`, `BOOST_AUTO_TEST_CASE` and `BOOST_FIXTURE_TEST_CASE`: the grammars read them as a function or as a call followed by a block, and the walker makes a function of each with the attributes `test`, `test-framework:`, `test-name:` and `test-suite:`. Impacted tests (`CTests` in `testmap.rs`) are `ctest --test-dir build -R '<regex>'` for what CTest knows by name (a discovery command, or `add_test(NAME x ...)` for a program in a test folder), else the executable with its framework's filter (`./build/<folder>/<target> --gtest_filter=A.B`, `--run_test=`, `--test-case=`, or Catch2's quoted names), else `ctest --test-dir build`; all `ctest` regexes fold into one run, each executable has its own, and past 8 names the run is whole. `build` is a guess: it is where `cmake -S . -B build` builds, and the commands say so by being the same ones the operations note prints; without CMake no command is derived. A changed source reaches the tests of its header (`add_c_pair_dependents`). Versions: `find_package(Name 1.2)` and `FetchContent_Declare(name GIT_TAG v1.2)` (and `CPMAddPackage`), `vcpkg.json` (`version>=`, `overrides` as the version in effect, `builtin-baseline` where no version is written), `conanfile.txt` and `conanfile.py` (`name/version`) and `conan.lock`, kept in `Unit::lock`. `vcpkg-lock.json` is not read: vcpkg has no lock file in manifest mode. Operations print `cmake -S . -B build`, `cmake --build build` and, when tests exist, `ctest --test-dir build`; presets are not followed because `binaryDir` is arbitrary, so no later command could name it.

**TypeScript and JavaScript** (`crates/cw-parse/src/jsbuild.rs`, `typescript.rs`; units in `units.rs`, commands in `crates/cw-wiki/src/pm.rs`, tests in `testmap/js.rs`): a file is the module `dir::file`, and an import specifier resolves in this order: relative (extensions, `index`, `./x.js` for `x.ts`), `compilerOptions.paths`, `baseUrl`, a workspace package by its `package.json` name, else an outside package (`JsRepo::resolve_import`, called from `scan_repo`). The config that applies to a file is the nearest `tsconfig.json` (else `jsconfig.json`) up the tree; JSONC (comments, trailing commas) is read, `extends` follows a relative file or a package under `node_modules` (and is skipped when it is not there), a config's own `paths` replace the inherited ones, targets are taken from `baseUrl` when one is set, else from the folder of the config that wrote `paths`, patterns have one `*` and the longest prefix wins, targets are tried in order. `references` change nothing; `tsconfig.app.json` and the like are read only through `extends` or when named `tsconfig.json`. A specifier a `paths` pattern matches is the repository's own whether or not a file is found (`parse_typescript_with`'s `is_alias`): it is never an outside package, so no integration note is planned for `@/x`. Bundler aliases (`vite.config.ts` `resolve.alias`, webpack) are code and are not read. A workspace is `pnpm-workspace.yaml` (`packages:` globs, block or flow, `!` excludes; a line-based reader) or `workspaces` in a root `package.json` (array or `{ packages }`); only packages a workspace lists resolve by name, to the first of `exports` (`.` or the subpath, conditions `source`, `import`, `module`, `default`, `require`, `node`, `types`), `source`, `module`, `main`, `types`, then `src/index` and `index`, with `dist`, `build`, `lib` and `out` mapped to `src`. A unit is a `package.json` folder; a dependency in any table on another package of the repository (`workspace:*` or a plain version) is a unit dependency, beside the ones from imports. **Package manager** (`JsRepo::manager_of`): the `packageManager` field of the nearest `package.json` that has one, else the lock file nearest above (`pnpm-lock.yaml`, `yarn.lock`, `bun.lock`, `bun.lockb`, `package-lock.json`, `npm-shrinkwrap.json`, in that order in one folder), else `pnpm-workspace.yaml` (pnpm), else npm; Yarn is Berry when the field says 2 or later, `.yarnrc.yml` is at or above the root, or the lock file holds `__metadata:`, else Yarn 1. `Unit::pm` holds it, with the folder installs run in; `Unit::lock` the lock file of it (`bun.lockb` is binary and is no lock). Commands (`pm.rs`): install is `npm ci`, `pnpm install --frozen-lockfile`, `yarn install --immutable` (Berry) or `yarn install --frozen-lockfile` (1), `bun install --frozen-lockfile` when there is a lock file, else `<manager> install`; scripts are `<manager> run <script>`; a package a workspace lists is named with the manager's filter (`npm -w <name> run`, `pnpm --filter <name> run`, `yarn workspace <name> run`, `bun run --filter <name>`), any other package below the root with `npm --prefix <dir>` or `cd <dir> &&`. **Locked versions** (`manifests.rs`, `JsLock`): `package-lock.json` and `npm-shrinkwrap.json` (lockfileVersion 1 to 3), `pnpm-lock.yaml` (lockfileVersion 6.0 and 9.0, the importer of the package's folder), `yarn.lock` (Yarn 1 by its header, Berry by `__metadata` version 4 to 9) and `bun.lock` (lockfileVersion 0 and 1); another format is read as no lock, and a version is never guessed. An installed description is read from `node_modules/<name>/package.json` in the package's folder, then the root, then pnpm's `.pnpm/node_modules`; a pnpm link is read through like a folder. **Impacted tests** (`testmap/js.rs`): test files are `*.test.*`, `*.spec.*`, `*.cy.*` and sources under `__tests__`, `test`, `tests`, `e2e` and `cypress`; tests are `test(`, `it(` and `describe(` calls with a string title (also `.only`, `.skip`, `.todo`), read from the text. The runner is what the file imports (`vitest`, `@playwright/test`, `node:test`, `bun:test`, `@jest/globals`), else the package's `test` script, else its dependencies, else the workspace root's; the command is `<exec> vitest run <files>`, `jest <files>`, `mocha <files>`, `playwright test <files>`, `ava <files>` through `pm::exec` (`npx`, `pnpm exec`, `yarn`, `bunx`; `npm -w <name> exec --`, `pnpm --filter <name> exec`, `yarn workspace <name>` for a workspace package), `node --test <files>` (after `cd` below the root), `bun test ./<path>` from the root; paths are those of the package's folder. A runner that is not known runs the `test` script whole (`pnpm run test`), also for a workspace package under bun, which has no filter that runs a program; no script, no command. One run for each package and runner over every impacted file, past 8 files the runner runs whole. End-to-end specs (Playwright, Cypress) are test files like the rest, and the import graph reaches them only through what they import (a page object, a helper), never from the app's own sources: no guess is made about what a page shows. Not read: bundler aliases, `tsconfig.app.json` beside a `tsconfig.json` that only has `references`, Yarn's `.pnp.cjs`, `bun.lockb`, `pnpm-lock.yaml` of lockfileVersion 5 and older, `catalog:` and `npm:` specifiers.

**Python** (`crates/cw-parse/src/pyroots.rs`, `lang.rs`; units in `units.rs`; tests in `testmap/python.rs`): a folder of `.py` files below a root is part of the dotted path whether or not it has an `__init__.py` (PEP 420). A **project** is a folder with `pyproject.toml`, `setup.py` or `setup.cfg`; its **roots** are a `src` folder holding `.py` files and what the build file declares: `[tool.setuptools.packages.find] where`, `[tool.setuptools.package-dir]` (`""` is a root, `name = "dir"` a package of that name), `[options] package_dir` and `[options.packages.find] where` of `setup.cfg`, the literals `package_dir={"": "src"}` and `where="src"` of `setup.py` (a path computed in code is not followed), `[tool.poetry] packages = [{ from }]`, `[tool.hatch.build.targets.wheel] packages` and `sources`, `[tool.pdm.build] package-dir`, `[tool.maturin] python-source`. A file under a root is named from it (`PythonRoots::module`); any other keeps the old rule: from the outermost folder with an `__init__.py`; with none, from its project's folder; with no project, from the repository root minus a leading `src` or `lib`. An absolute import resolves from any module name, so it needs no root of its own. **Units**: a file of a regular package (an `__init__.py` above it) belongs to the unit of its top-level package, as before, so a repository where every folder has an `__init__.py` has the notes it had; every other file (namespace folders, loose scripts, `tests/` beside `src/`) belongs to its project's unit, named by `[project] name` or `[tool.poetry] name` (else the folder), and one that is at the repository root or has no project to the repository's own unit, named by the repository, as before. So a loose scripts folder with no build file joins the root unit, no longer a unit for each folder. Module names change where a file gets a root it had none (`svc/src/shop/orders.py` with a new `svc/pyproject.toml` goes from `svc::src::shop::orders` to `shop::orders`), and with them note ids and paths: an explained note keeps its words through `carry_moves` when the subject keeps its kind and name and is the only candidate (`an_explained_python_module_survives_the_change_of_its_module_path`), and the first sync after such a change says `Moved N notes` and rewrites the unit's note and the folder maps. **Impacted tests**: test files are `test_*.py`, `*_test.py` and anything under `tests` or `test`; `conftest.py` is support and holds no test. A test is a function `test_*`, a method `test_*` of a class `Test*` (pytest) or of a class whose base ends in `TestCase`, directly or through a base of the same file. The runner is pytest when the project names it (`[tool.pytest`, `pytest` in a build file, `requirements*.txt` or `Pipfile`, `pytest.ini`, `[pytest]` in `tox.ini`, `[tool:pytest]` in `setup.cfg`, a `conftest.py`) or the file imports it, else `python -m unittest`. The project's tool leads the command when its files say which: `uv run` (`uv.lock`), `poetry run` (`poetry.lock` or `[tool.poetry]`), `pdm run` (`pdm.lock`), `hatch run` (`[tool.hatch.envs`). `pytest tests/test_x.py::test_a tests/test_x.py::TestC::test_m`, or `python -m unittest tests.test_x.TestC.test_m` (unittest runs methods only, by the module name the scan gave, so the package must be importable from where it runs); a project below the root is entered with `cd <folder> &&` and its paths are its own. One run for each project and runner; past 8 names the files, past 8 files the whole project (`pytest`, `python -m unittest`).

```
cargo test -p cw-wiki                 # one crate
cargo test -p cw-wiki --test health   # one file in crates/cw-wiki/tests/
cargo test -p codewiki-app themes::   # tests whose path contains the filter
```

To run the app:

```
cargo build -p codewiki
cargo run -p codewiki-app -- <repo> [<view>]
```

The RustRover run configurations in `.run/` do the same; `codewiki-app` builds `codewiki backend` first. `scripts\clean.ps1` keeps exactly those two dev builds and prunes every other debug artifact.

To build the package:

```
pwsh scripts\package.ps1              # dist\CodeWiki-<version>-windows-x64.zip and -setup.exe
```

After the zip, `package.ps1` builds `dist\CodeWiki-<version>-windows-x64-setup.exe` from `scripts\setup\codewiki.iss` when Inno Setup 6's `ISCC.exe` is found (on `PATH`, in `C:\Program Files (x86)\Inno Setup 6\` or in `%LOCALAPPDATA%\Programs\Inno Setup 6\`). `-NoSetup` skips it. Without ISCC it says so and still builds the zip. The setup program runs `install.ps1` from the zip's files and `uninstall.ps1` on uninstall, and is unsigned.

`package.ps1` builds with line tables and without stripping (`CARGO_PROFILE_RELEASE_DEBUG`, `CARGO_PROFILE_RELEASE_STRIP`; the profile in `Cargo.toml` stays as the Docker image needs it), so each program gets a PDB file. It copies each program and its PDB to `dist\symbols-<version>\` for Sentry and keeps them out of the zip. With `CODEWIKI_SENTRY_DSN` set, the programs carry that DSN.

## CI

`.github/workflows/` holds five workflows, and the root holds an action:

- `ci.yml` runs the four commands above, with `--locked`: format, clippy and the tests on Windows, and `cargo deny` on Linux in two legs (advisories; bans and sources). The licenses of dependencies are not checked, by the owner's decision of 2026-11-20: `deny.toml` has no list of allowed licenses, so a bare `cargo deny check` fails on every crate. The advisories leg can fail with no change in this repository, when a new advisory is published: fix the dependency, or add the advisory's ID to `ignore` in `deny.toml` with a reason. Its job `wiki-check` runs CodeWiki on this repository, on Linux: `codewiki check` uploads its findings to code scanning and never fails the build, and `codewiki update` does fail it. The wiki in `obsidian/` must be what the commit's code generates: the sync there may change nothing but `last_indexed_commit` in the manifest. So a push that changes code, a script, a workflow or a manifest carries its `docs(wiki)` commit (`cargo run -p codewiki -- update` at the repository root); a change to README, ROADMAP, this file or the guide needs none. Three things keep the result the same on every machine. A source file is hashed with CRLF read as LF (`cw_core::source_hash`), because git hands out one file with either ending. The sync counts every file it finds, tracked or not, so sync in a tree with no stray files, and put a folder that is no part of the project into `.codewikiignore`, where `docs/guide/` is. And the job writes `codewiki.sarif` outside the checkout. Dependabot cannot sync, so its pull requests skip the step, and the push that merges one must bring the sync.
- `action.yml` at the root is a GitHub Action for other repositories (`uses: Fly-onlyone/CodeWiki@action-v1`; README, "GitHub Action"). It never builds this repository: it uses a released CodeWiki. On a Linux runner it puts a script named `codewiki` on `PATH` that runs the image `ghcr.io/fly-onlyone/codewiki:<version>` as the runner's user, with the workspace and the temporary folder mounted at their own paths; on a Windows runner it takes `codewiki.exe` from the release's zip and checks the `.sha256`. Then it runs `codewiki check` and, for `wiki: check` or `update`, the sync, with the same comparison as `wiki-check` here. `action-test.yml` uses it as a stranger would, on a small repository made in the job, on `ubuntu-latest`, `ubuntu-22.04` and `windows-latest`; it runs when either file changes. The action's tags are `action-v<n>` (move `action-v1` for a change that breaks no caller): a tag that starts with `v` starts `release.yml`. A release that renames the zip, moves the binary in the image or changes the commands' options breaks the action: run `action-test.yml` by hand (`workflow_dispatch`) after each release.
- `security.yml` runs gitleaks over new commits. Never commit a secret, not even a test value that looks real. A confirmed false positive goes in `.gitleaksignore` by its fingerprint.
- `release.yml` and `docker.yml` run on a `v*` tag. The tag must equal `v` plus the workspace `version` in the root `Cargo.toml`. A tag publishes the Windows zip, the setup program and a `.sha256` for each as a GitHub Release, and pushes the image to GHCR. `release.yml` also builds the package, without publishing, on pushes to main and on pull requests that change `scripts/setup/**`, `package.ps1`, `install.ps1`, `uninstall.ps1` or `release.yml`. Do not push a tag unless asked. The package carries the DSN of the repository variable `SENTRY_DSN`; after the release, the programs' debug files (`dist\symbols-<version>\`, written by `package.ps1` and never put in the zip) go to the Sentry project `fly-theonlyone/codewiki` with `sentry-cli`, when the secret `SENTRY_AUTH_TOKEN` is set. The token is given to that step alone, never to the build.

Dependabot (`.github/dependabot.yml`) opens weekly update pull requests and leaves `gpui-kit` alone.

## Checking the app without taking focus

Start `codewiki-app <repo> <view>` with `CODEWIKI_INSTANCE=new` in its environment (without it, the launch hands over to an app that is already running, and that one comes to the front), where `<view>` is a note name or one of `home:` (the default), `graph:`, `palette:<query>` (opened over Home), `edit:<note>`, `review:` (the Review page), `waiting:` (the Waiting notes page; the palette has "Show waiting notes"), `settings:` or `settings:<category>` (`appearance`, `search`, `backend`, `repositories`, `updates`, `keyboard`, `diagnostics`), `themes:`, `health:`, `contracts:` and similar. `_HOME` opens the wiki map note. Capture the window with `PrintWindow` and post input with `PostMessage`; do not bring the window to the front, and never capture the whole screen. Start it with `System.Diagnostics.ProcessStartInfo` (`UseShellExecute = false`, `CreateNoWindow = true`, the environment through `.Environment`). `Start-Process -WindowStyle Hidden` hides the GPUI window itself: there is then no window to capture or post keys to.

The window is glass over the Windows backdrop, which a capture cannot see. Set `CODEWIKI_BACKDROP=#RRGGBB` to paint an opaque color under the glass, `CODEWIKI_BACKDROP_DRIFT=1` to keep the backdrop drifting while the window is inactive, and `CODEWIKI_MOTION_SCALE=<n>` to slow every animation by `n` so that a capture can catch one half way. Closing the app's window (`WM_CLOSE`) hides it and ends nothing. To end the app and its backend, start it on `palette:Quit CodeWiki` and post Enter (`WM_KEYDOWN`, `0x0D`), or end it by force and stop its backend (`POST /v1/shutdown` with the token from `backend.json`). An app ended by force (`taskkill`, a crash) leaves its backend running; stop that one too when a check ends. Give a check its own `CODEWIKI_DATA_DIR` and `APPDATA`, so that it shares no backend, no settings and no instance with the owner's app. A click with Ctrl or Shift needs the modifier state to be set: GPUI reads it with `GetKeyState`, not from the `MK_*` flags of the posted message, so a check attaches its thread to the window's thread (`AttachThreadInput`) and sets the keys with `SetKeyboardState`, which needs no focus. What needs the window brought to the front (a click on a Windows notification, a click on the tray icon, the tray menu, a second launch without `--tray`) is checked in the VM, not here.

## Testing a package in a clean Windows

`scripts/vm` drives a Hyper-V guest from the host: `provision.ps1` installs Windows unattended and takes the checkpoint `clean`; `provision-gpu.ps1` adds the checkpoint `clean-gpu`, the same guest with the host's graphics driver in it; `test-release.ps1` restores `clean` (or, with `-Gpu`, `clean-gpu` and attaches a share of the host's graphics card; `-VmName`, `-User`, `-Password` and `-Snapshot` name another guest, account and checkpoint), installs the newest zip in `dist\`, runs the cases and writes `report\vm-test-<date>\` (screenshots, a recording, `logs\results.json`). `Vm.ps1` holds the helpers, `record.ps1` films the screen, `guest\probe.ps1` runs inside the guest and reports what is installed and running. A run ends with a `report.md` in that folder that opens with a summary. `report\` is not in git; on the development machine `report\vm-test-2026-11-21-0.3.0\report.md` is the model. It needs the account in "Hyper-V Administrators", `oscdimg.exe` from the Windows ADK for provisioning, and `ffmpeg` for the recording.

What the first runs taught, and the scripts now assume:

- A command sent over PowerShell Direct runs elevated and without a desktop. What a user would do goes through `Invoke-GuestScript`, `Invoke-GuestExe` and `Start-GuestExe`, which use the logged-in desktop session.
- A window opened by `Start-GuestExe` has no keyboard focus. Call `Show-GuestWindow` before `Send-Keys`, or the keys go to the desktop. It also returns the window's position, which click positions are measured from.
- Never name a helper `Start-Vm` or `Stop-Vm`: PowerShell ignores case, so it replaces the Hyper-V cmdlet and calls itself.
- Hyper-V starts a guest only when all its memory is free on the host. 2048 MB is enough for a stripped image.
- Without `-Gpu` the guest has no graphics processor and Direct3D runs on the processor. The drifting backdrop once took every core there, so it now stands still on a software adapter (`backdrop.rs`). P1 measures the idle load with `Get-GuestProcessorLoad`, which asks the host; should it ever starve the guest again, the test sets motion to "reduced" to go on. Run both passes for a change to drawing or motion: they are two different user machines.
- With `-Gpu` the guest shares the host's card, which Microsoft does not support on a Windows 11 host. After a graphics driver update on the host the guest's driver copy is stale: run `provision-gpu.ps1 -Force`. A low idle load proves the card only together with a picture: on some Windows builds the guest then draws nothing at all (`Test-GuestDisplay` in `Vm.ps1` explains and checks it).
- `Show-GuestWindow` clicks the window, and that click is input: it hides any defect where the app waits for input to draw. The F2 cases start the app and leave it alone.
- A guest command that times out prints nothing. Treat empty output as a failed probe, never as "nothing is running".
- A guest account may have no password: pass `-Password ""`. PowerShell Direct then needs `LimitBlankPasswordUse = 0` under `HKLM\SYSTEM\CurrentControlSet\Control\Lsa` in the guest. The guest's folders are read from the guest (`C:\Users\Software Tester` has a space; a program path given to Task Scheduler must be quoted).
- Never take a program's window from `MainWindowHandle`. With the pointer resting where the app's close button appears, that handle is the tooltip Windows shows for the button, and every click measured from it misses. `Show-GuestWindow` and `Get-GuestWindowInfo` take the largest visible window of the process.
- A click right after its own pointer move reaches a control that has just been redrawn for the hover. Use `Send-RestedClick` (move, rest, press) for anything that might stop answering while the pointer rests on it; the title bar's buttons once did.
- Closing the app's window hides it; only Quit ends the app, and its backend with it. The next start then brings up a new backend and takes longer; `Stop-GuestApp` ends the app by force and leaves the backend. Wait longer after a real Quit. An app left hidden takes the next `Start-GuestApp`: the launch hands over to it, so state from the case before (tabs, an open editor) is still there. End the app between cases that must start clean.
- The host must have the guest's whole memory free each time the guest starts, a restart in the middle of a run included. `Start-Guest` frees memory when there is too little and tries once more.
- With `-OldZip <older package>` case U2 installs the older version and has it update itself to the package under test, which `guest\update-server.ps1` serves in the guest in GitHub's place (`CODEWIKI_UPDATE_URL`, set for the guest's user). An older package needs the workspace version and the crates' requirements on each other lowered together (`version = "0.1.0", path` in the manifests), built without `--locked`, and none of it committed. With `-ReleaseTag` case R1 downloads the published package in the guest and compares checksums; with `-RealRelease` U2 asks the real GitHub.
- With `-Hardened`, `guest\harden.ps1` turns Windows' own protection up before anything is installed: today's definitions, the cloud block level at zero tolerance, controlled folder access, network protection, every attack surface reduction rule on block, UAC on "always notify", SmartScreen on block. ## Releasing

The `qingyi:ship-release` skill runs a release and reads its facts from this section.

- **Checks.** The four commands under Commands.
- **Version.** `version` in the root `Cargo.toml`, the `version = "<old>", path` requirements in `crates/*/Cargo.toml`, `plugins/claude-code/.claude-plugin/plugin.json` and `plugins/codex/.codex-plugin/plugin.json`; `crates/codewiki/tests/plugins.rs` fails when a plugin is missed. Then run `cargo check --workspace` once without `--locked`: it rewrites `Cargo.lock`, which the package build and CI then hold to. Commit as `chore(release)`.
- **Previous package.** Before the bump: `gh release download v<previous> --repo Fly-onlyone/CodeWiki --pattern "*.zip*" --dir dist\old`, then check it against its `.sha256`. A package built before the bump has the old version's name and replaces the zip in `dist\`.
- **Highlights.** Before the tag, write `docs/releases/<version>.md`: 3–6 bullets, for users, on what the release brings. Commit it as `docs(release)`. `release.yml` puts it on top of the release notes, which `scripts\release-notes.ps1` builds from the conventional commits since the previous release (GitHub's generated notes list only pull requests, and work here lands by local merges). Preview the notes with `pwsh scripts\release-notes.ps1 -OutFile <scratchpad>\notes.md`; to rewrite a published release's notes, run it with `-Tag v<version>` and pass the file to `gh release edit v<version> --notes-file`.
- **Package.** `pwsh scripts\package.ps1`.
- **Publish.** After the push, wait for `ci.yml` and `security.yml`. The tag `v<version>` starts `release.yml` and `docker.yml`; `gh release view v<version>` then shows four files: the zip, the setup program and a `.sha256` for each, under the notes from `scripts\release-notes.ps1`.
- **Docs.** `ROADMAP.md` (date, crate and test counts, what is now verified, the VM run), `README.md` (status line, features), this file (what a later agent must know about the new parts), and the wiki: `cargo run -p codewiki -- update` at the repository root, with `obsidian/` committed as `docs(wiki)`.
- **User guide.** README links to it: the GitBook site "CodeWiki" (organization "Fly", https://fly-3.gitbook.io/codewiki/). Since 2026-11-28 its source is in this repository, in `docs/guide/`, through GitBook's Git Sync on `main`: `gitbook-docs.yaml` at the root maps the site's one space (`key: space-1`) to that folder, which holds `README.md` (the first page), `SUMMARY.md` (the table of contents: a page file that is not listed in it is not imported, and each file may be listed once), the pages, and `.gitbook/assets/` with the pictures. The sync goes both ways. A push to `main` that touches `docs/guide/` is imported and published by the sync, with no review, and an edit or a merged change request in GitBook's editor arrives here as a commit whose subject starts with `GITBOOK-`, pushed to `main`: `git pull --ff-only` before committing, and never rewrite pushed history. So the guide changes only in the commit that records a published release, after the release's check, never together with a feature: it must not describe a version nobody can download. For each release, bring every page the release touches up to date, checked against the code, with screenshots from the guest run (`-GuideShots`), saved into `docs/guide/.gitbook/assets/` and referenced by a relative path (`../.gitbook/assets/<name>.png` from a page one folder down). Pages are GitBook's Markdown: keep its blocks (`{% hint %}`, `{% stepper %}`, `{% tabs %}`) as they are, and keep a page's file name, which is its address. Never change `key` in `gitbook-docs.yaml`: a new key is a new, empty space. To move the folder, move the files and change `content.directory` in one commit. `.gitbook/` cannot live apart from the pages: it belongs to the space's folder. After the push, read a changed page on the public site. The GitBook MCP tools still read the site; a merge through them needs the owner's word each time.
- **Clean-up.** `pwsh scripts\clean.ps1`.

## App look

The look lives in `crates/codewiki-app/src/`: `glass.rs` (how opaque each surface is), `reading.rs` (note typography), `icons.rs`, `motion.rs` (whether things move), `backdrop.rs`, `constellation.rs` and the `mui/` module.

The backdrop has two layers under the glass. The color glow (`backdrop.rs`, the shapes) lies behind everything, and `glass` fits the chrome's opacity to its `STRENGTH`, so it stays faint. The sky (`constellation.rs`: a fixed graph of notes and links, its pulses and their schedule) is drawn only in the clear margins beside a page's reading column, which the app reports to the shell through `backdrop::Margins`: a margin holds no text, so its glass (`Levels::margin`) can be clear and the sky strong without a contrast limit. Never draw the sky behind the chrome or the column. A page gets margins from `glass::reading_surface` when it has a centred column (notes, generated pages, Home) and room for them; the bars above the page then carry the pane's surface themselves. Pulses come more often while a wiki is written: `AppView::tell_backdrop` sets `backdrop::set_writing` from the app's own sync and from `updating` in `/v1/status`. "Background graph" (Settings → Appearance, `backdrop.txt`) turns off the glow, the sky and the clear margins.

`mui/` holds the controls, drawn to Material UI's measurements with the TradingAgent theme's changes; where the two differ, TradingAgent wins. Draw a control with a `mui` component, not with a gpui-kit one and not by hand. A number copied from MUI or TradingAgent names its source file in a comment. Springs and entrances come from `mui/motion.rs`, `TOAST_HOLD` and the toast's entrance (`Enter::TOAST`) among them; do not write a duration or a spring anywhere else. The toast is `mui/snackbar.rs`, and the check box of the review queue is `mui/checkbox.rs` (`Check`: unchecked, checked, indeterminate; `ListItemButton::leading` puts it before a row). GPUI cannot scale an element, blur what is behind one, or clip to rounded corners; `mui/mod.rs` and `mui/ripple.rs` say how each is worked around.

How strongly a control answers hover, press and selection is one set of values, `DARK` in `mui/interaction.rs`, which every `mui` control reads through `interaction::current`; do not write such a fill, shift or lift in a component. The values are stronger than MUI's and TradingAgent's, chosen by eye on 2026-11-25. A light theme takes the state fills at half strength and each lift as a darkening (`Interaction::for_mode`); rows keep their fills. A changed value must keep `every_bundled_theme_reads_in_its_selected_and_hovered_states` in `themes.rs` passing, which holds the selected row's label, a hovered link and a switched-on icon to their contrast on every bundled theme. Links in notes take their hover look through `LinkHoverStyle`, a global that only the patched copy of gpui-base in `vendor/gpui-base` has (`reading::sync_link_hover` sets it). The same copy lets a `TextViewState` report its headings and where a block starts (`DocumentHeading`, `headings`, `block_top`, `markdown_headings` in `src/text/state.rs`), which the outline needs. A gpui-kit bump must copy the new gpui-base and patch it again (NOTICE lists the files), or drop the patch once gpui-kit has the features (the link look is asked in https://github.com/longbridge/gpui-kit/issues/4116).

The details pane scrolls when its content is longer than the window. Its outline lists the `##` headings the note's body draws (`outline.rs`), so an entry never points at a heading the body parsed differently. A click glides the body to the heading over `mui::motion::glide` (at once with reduced motion) and keeps the entry lit until the user scrolls; otherwise the entry of the section being read is lit (`outline::spy`). The app owns the note's `TextViewState` (`Reader` in `main.rs`) and the editor's preview (`Editing.preview`), so it can read and scroll them; while a note is edited, the outline follows and scrolls the preview.

The whole app zooms (Ctrl+wheel, Ctrl+= / Ctrl+- / Ctrl+0, the palette, Settings → Appearance; `zoom.rs`). GPUI cannot change a window's scale, so a size written as an `f32` is in design units and `crate::zoom::px` turns it into GPUI's pixels at the current zoom; the app's modules import it in place of GPUI's `px`, and a pixel value turned back into a number (`width / px(1.)`) is in design units too. `zoom::sync_theme` scales the theme's font sizes and radii, which moves the rem and with it every gpui-kit control. GPUI's own `px` is for what keeps the screen's pixels at every zoom (the window's measures, the backdrop's shapes, the hairline); clippy refuses it elsewhere (`crates/codewiki-app/clippy.toml`), and each such use carries an `#[allow]` that says why. Never mix the two in one expression: `px(x / gpui_kit::px(1.))` zooms twice. The title bar stays at 100%, as a browser's does: the shell builds it in `zoom::unscaled` and lays it out in `zoom::FixedRem`. The shell takes Ctrl+wheel in the capture phase, before anything under the pointer can scroll or zoom itself. Mermaid diagrams in a note keep their size.

A note narrows a wide diagram to its column, where a sequence of twelve parts is drawn at 28% and cannot be read. The image element is gpui-base's, so the note cannot scroll it or draw it larger. A drawn diagram is therefore a link (`markdown::OPEN_DIAGRAM_SCHEME`, written by `prepare_note_with`), and a click opens the diagram viewer over the window (`AppView::open_diagram` and `diagram_viewer_view` in `main.rs`): fitted, and never above its natural size. The wheel zooms about the pointer, a drag moves the diagram, `+`, `-`, `0` (fit) and `1` (natural size) do the same as the header's buttons, and Escape, the close button or a click outside closes it. `diagram_view.rs` holds the geometry and its tests; it looks at the diagram through `graph::Camera`, with limits of its own. The viewer shows the note's picture at once and has the diagram drawn again at twice the pixels off the UI thread (`cw_mermaid::render_png_scaled`), so that it stays sharp; one such picture is kept, and the one it replaces is handed back to GPUI with `Image::remove_asset`, because each is tens of megabytes decoded. The viewer's sizes go through `zoom::px`, so it follows the app's zoom, and Ctrl+wheel stays the app's zoom inside it. Closing only clears a flag: `render` gives the focus back, since not every way to close has the window.

A generated page is a `Doc` (`doc.rs`): a page function in `pages.rs` or `live.rs` builds it from backend data, `doc_view.rs` draws it, and each link, row and button carries an `Action` that `AppView::run_action` carries out. Do not build a page as Markdown; only notes are Markdown. A page function has a test that reads its `Doc`.

An `Action::Note` names a note by its whole vault path, `.md` included, or by its bare name: the backend's `find_entry` (`cw-wiki/src/query.rs`) knows those two and nothing else, so a folder path without `.md` is "not found".

The toolbar's search box suggests while it is typed in. `suggest.rs` holds the list's state and keys; `mui::autocomplete::Listbox` draws it under the box. Each change of the text replaces the lookup before it (dropping the task cancels it); the lookup waits `suggest::PAUSE` and asks `GET /v1/repos/{id}/search?mode=text`, which searches words only and never calls the embedder. It does not go through `AppView::run`, so it sets no busy line and clears no error. The box keeps the focus: the root's capture handlers give Up, Down and Escape to the open list, as they do for the palette, and Enter opens the highlighted hit or else runs the full search. A row's press never moves the focus (`mui::base`), so the list chooses a row on click and closes when the box loses the focus. `live::hit_target` and `live::hit_groups` turn a hit into what it opens, for the list and the Search page alike; `live::plain_snippet` turns a note's snippet into one line of plain text.

The app's keyboard shortcuts (the palette, tabs, Back, save, the side panes, Settings) are actions handled by `shortcuts` in `main.rs`. Both the app's root and the page the shell draws (`DocPage`, through `doc_view::Shortcuts`) use it, because a generated page is drawn beside the app's view, not inside it: an input or a button focused there, such as Home's search field, is outside the root's element tree, and in the first build of 0.6.0 Ctrl+K did nothing on a freshly started Home. A new shortcut goes into `shortcuts`, never onto the root alone. A start argument (`edit:`, `palette:`, `settings:`, a view) is carried out while a frame is built, where a `cx.notify()` asks for no frame; `render` therefore sets `start_settling` and calls `doc_view::notify_after_draw`, and the `page drawn` line waits for that frame (`ready::Holds`).

The Settings page (`Page::Settings(Category)`) fills the window, as Home does. `settings.rs` names its categories and the fields that are typed; `settings_pages.rs` builds the `Doc` of each category from a `Model`; `settings_view.rs` holds its state and draws the frame. Its `Doc` is drawn by the app's view, with `doc_view::column`, and not by the cached page view: a text input and the list of a select take their events through the view that owns them, as the search box and the theme menu do. So `Block::Switch`, `Select`, `Field` and `Secret` work only on a page drawn that way. A text input needs a window to be made and must outlive the frames, so the app's view makes one for each `FieldId` at its start. A change is applied when it is made: a field saves itself on Enter or when the focus leaves it, and also when its page is left, because the field is gone by then and reports nothing. The measures of the layout that are a matter of taste are in `settings_layout.rs`; numbers copied from MUI stay in `mui/`.

A module that brings in the kit with `use gpui_kit::*` must not write `use super::*` in its tests: the glob carries GPUI's own `test` attribute, which then stands in for the standard one and fails with "recursion limit reached".

The title bar is drawn by the shell (`backdrop.rs`), in every frame, not by the app's view, which the shell draws from its cache. GPUI does not keep the window control areas of a cached view, so a title bar inside one has dead minimize, maximize and close buttons and cannot drag the window. Keep anything that calls `window_control_area` out of a cached view.

A `cx.notify()` made while a frame is being drawn (in `render`, or a canvas callback) marks the view but asks for no new frame, so the change waits for the next input. From such code, call `doc_view::notify_after_draw`. Under reduced motion, pages once stayed blank until the pointer moved because of this.

Icons are Material Icons, as SVG files in `crates/codewiki-app/icons/`. Every icon the app draws is a constant in `icons.rs`; a file that is not listed there is not embedded. A new palette command needs an arm in `icons::for_command`. A text color added to a CodeWiki theme must pass the contrast test in `themes.rs`, which checks it on the page and on a card.

Color comes from the active theme, never from a hex value in code, so every theme shows its own hue. Chrome surfaces (title bar, sidebar, toolbar, tab bar, details) are filled with `glass::tinted` and the reading pane with `glass::tinted_pane`; both mix in 6% of the theme's primary color (`CHROME_TINT`, `PANE_TINT` in `glass.rs`). Section labels are in the theme's link color. In notes (`reading.rs`), H1 to H3 take the link, magenta and cyan colors, and list markers, inline code, code blocks, table heads and quotes are tinted; body text stays neutral. A sidebar or toolbar icon takes its color from `icons::hue`, and an icon with no hue there stays neutral. Every theme except CodeWiki's own is redrawn on the CodeWiki set's levels when it is applied (`standard.rs`): each color role takes the lightness and saturation the CodeWiki themes of the same mode give it, in the theme's own hues, and text is nudged until it reads. Syntax colors are left alone. The text colors of every bundled theme must reach WCAG AA on the page, on a card and on the tinted page, and icon hues 3:1 (tests in `themes.rs` and `standard.rs`); a change to `codewiki.json` that breaks this is fixed in the colors, not in the tests. `glass` fits the chrome's opacity to the foreground, muted and link colors on the tinted surface, so a weak text color makes the chrome denser rather than unreadable.
