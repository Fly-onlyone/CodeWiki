# CodeWiki — agent instructions

CodeWiki is a Windows-only native desktop app plus a Rust backend that generates and maintains a codebase wiki (an Obsidian vault at `<repo>/obsidian/`) for humans and coding agents. `ROADMAP.md` records what is built and what is verified.

## Hard rules

- **Licenses.** No AGPL, GPL, LGPL or EPL dependencies. `cargo deny check` must pass. `merman` is used with `default-features = false`; the `forceatlas2` crate is banned.
- **No WebView.** The UI is native Rust on GPUI (`gpui-kit`). Do not add a browser, WebView2 or Electron dependency.
- **The app talks HTTP only.** `codewiki-app` gets all data from the backend through `cw-client`. It may link `cw-illustrate`, `cw-mermaid` and `openui-lang` to draw, never the index, parser or wiki crates.
- **Never overwrite a human-edited note.** Changes to such notes go through the proposal queue.
- **The index is a cache.** Everything in it must be rebuildable from the repository and the vault. Bump `SCHEMA_VERSION` in `crates/cw-index/src/schema.rs` on any schema change; old indexes are dropped and rebuilt.
- **Keep builds small.** Do not loosen the `[profile.dev]` settings in the root `Cargo.toml`; debug builds once reached 44 GB. Run `pwsh scripts\clean.ps1` after long sessions.

## How the parts connect

- **Who opens the index.** The CLI and `codewiki serve` (`cw-server`) open the index directly. The app and the MCP bridge never do: they call `cw_client::Backend::connect` in `crates/cw-client/src/lib.rs`, which uses the first of these that works:
  1. `CODEWIKI_URL` with `CODEWIKI_TOKEN`.
  2. The URL and token in `backend.json` in the data directory, when `/v1/health` answers.
  3. A new `codewiki serve`, started from the binary beside the caller or from `PATH`.

  A backend started before a rebuild keeps serving the old code. Stop it after changing a backend crate.
- **Where state lives.** The index and the backend's state are in `cw_core::paths::data_dir()`: `CODEWIKI_DATA_DIR` when set, otherwise `%LOCALAPPDATA%\CodeWiki`. The vault is `<repo>/obsidian/`.
- **Generation.** `cw_wiki::service` holds the operations that the CLI, the server and the MCP tools share. `service::update` rescans the repository into the index, then `generate::generate` scans, plans, freezes names, renders, lints and writes. `cw_vault::lifecycle` decides for each note whether it is written, proposed or left alone. Bump `TEMPLATE_VERSION` in `crates/cw-wiki/src/generate.rs` when a rendering change should refresh every note.
- **The LLM plugs in from above.** `cw-wiki` defines the `ProseWriter` trait. `cw-llm` depends on `cw-wiki` and implements it as `LlmWriter`, so `cw-wiki` must never depend on `cw-llm`. `cw_llm::provider::from_env` picks the provider from `CODEWIKI_LLM`; `cw_embed::from_env` picks the embedder from `CODEWIKI_EMBED`. Without a writer, a note keeps its structural draft.
- **Tests.** Unit tests sit beside the code. `crates/cw-wiki/tests/` has one file per analysis plus `pipeline.rs`; the server's routes are tested in `crates/cw-server/tests/api.rs`. `wire.rs` in `cw-llm` and in `cw-embed` drives each HTTP provider against a stand-in server, so no API key is needed.
- **Orientation.** `obsidian/00-Architecture/` holds the generated crate dependency flow and the startup flows of `codewiki` and `codewiki-app`.

## Adding a feature

A backend feature usually touches four places: the logic in `crates/cw-wiki/src/`, a route in `crates/cw-server/src/api.rs`, a subcommand in `crates/codewiki/src/main.rs`, and a tool in `crates/codewiki-mcp/src/main.rs`. An app page is a page function that builds a `Doc` in `crates/codewiki-app/src/pages.rs` or `live.rs` (see App look), plus a palette entry in `palette.rs`.

## Commands

```
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo deny check
```

Run all four before reporting work as complete.

CI runs `cargo fmt --all -- --check`, clippy and the tests on Windows, and `cargo deny` on Linux in two legs. The advisories leg can fail with no change in this repository, when a new advisory is published: fix the dependency, or add the advisory's ID to `ignore` in `deny.toml` with a reason.

To run fewer tests:

```
cargo test -p cw-wiki                 # one crate
cargo test -p cw-wiki --test health   # one file in crates/cw-wiki/tests/
cargo test -p codewiki-app themes::   # tests whose path contains the filter
```

To run the app:

```
cargo build -p codewiki
cargo run -p codewiki-app -- <repo> [<view>]
```

The RustRover run configurations in `.run/` do the same; `codewiki-app` builds `codewiki backend` first. `scripts\clean.ps1` keeps exactly those two dev builds and prunes every other debug artifact.

## Verifying third-party APIs

Check crate APIs against docs.rs or the crate source for the pinned version before using them. GPUI is pre-1.0 and exact-pinned; do not bump it as a side effect of other work.

## Checking the app without taking focus

Start `codewiki-app <repo> <view>` where `<view>` is a note name or one of `graph:`, `palette:<query>`, `edit:<note>`, `settings:`, `themes:`, `health:`, `contracts:` and similar. Capture the window with `PrintWindow` and post input with `PostMessage`; do not bring the window to the front, and never capture the whole screen.

The window is glass over the Windows backdrop, which a capture cannot see. Set `CODEWIKI_BACKDROP=#RRGGBB` to paint an opaque color under the glass, `CODEWIKI_BACKDROP_DRIFT=1` to keep the backdrop drifting while the window is inactive, and `CODEWIKI_MOTION_SCALE=<n>` to slow every animation by `n` so that a capture can catch one half way. The app starts a backend process that outlives it; stop that one too when a check ends.

## App look

The look lives in `crates/codewiki-app/src/`: `glass.rs` (how opaque each surface is), `reading.rs` (note typography), `icons.rs`, `motion.rs` (whether things move), `backdrop.rs` and the `mui/` module.

`mui/` holds the controls, drawn to Material UI's measurements with the TradingAgent theme's changes; where the two differ, TradingAgent wins. Draw a control with a `mui` component, not with a gpui-kit one and not by hand. A number copied from MUI or TradingAgent names its source file in a comment. Springs and entrances come from `mui/motion.rs`; do not write a duration or a spring anywhere else. GPUI cannot scale an element, blur what is behind one, or clip to rounded corners; `mui/mod.rs` and `mui/ripple.rs` say how each is worked around.

A generated page is a `Doc` (`doc.rs`): a page function in `pages.rs` or `live.rs` builds it from backend data, `doc_view.rs` draws it, and each link, row and button carries an `Action` that `AppView::run_action` carries out. Do not build a page as Markdown; only notes are Markdown. A page function has a test that reads its `Doc`.

Icons are Material Icons, as SVG files in `crates/codewiki-app/icons/`. Every icon the app draws is a constant in `icons.rs`; a file that is not listed there is not embedded. A new palette command needs an arm in `icons::for_command`. A text color added to a CodeWiki theme must pass the contrast test in `themes.rs`, which checks it on the page and on a card.

Color comes from the active theme, never from a hex value in code, so every theme shows its own hue. Chrome surfaces (title bar, sidebar, toolbar, tab bar, details) are filled with `glass::tinted`, which mixes in the theme's primary color; section labels are in the theme's link color; body text stays neutral. A sidebar or toolbar icon takes its color from `icons::hue`, and an icon with no hue there stays neutral. The icon hues of the CodeWiki themes must reach 3:1 on the page and in the sidebar (a test in `themes.rs`). `glass` fits the chrome's opacity to the foreground, muted and link colors on the tinted surface, so a weak text color makes the chrome denser rather than unreadable.
